# Yuppers

Send a yup: a two-person agreement, written together, signed electronically, then tracked until each side has delivered. Nothing here moves money; it keeps a versioned agreement and a shared record of what each party says was done.

What a person makes and sends is a yup. In the code, the API and the database it is still an exchange (`Exchange`, `/v1/exchanges`, the `exchange` table), the technical name that predates the brand; the wording says yup in everyday places and agreement wherever someone commits to something or deals with a problem.

The design guide is kept in a separate, private repository. Comments and documents here cite it by section, as in `DESIGN.md §13.2`; the code and its tests are the public statement of how things work.

## Layout

| Path | What it is |
|---|---|
| `backend/` | Rust service: Axum, sqlx, PostgreSQL. One crate, six binaries. |
| `apps/web/` | React web app built with Vite. Also the no-install path for invited counterparties. |
| `apps/mobile/` | iOS and Android app: React Native with Expo, routed with Expo Router. The web app's flows for agreeing an exchange and seeing it through, on its own screens. |
| `docs/operations.md` | Running the service: deployment, health, logs, metrics, backups and restore. |
| `docs/wallet.md` | Apple Wallet and Google Wallet passes: what a pass shows and why, how it is signed and kept up to date, the settings, and the owner's steps once the accounts exist. |
| `docs/mobile-release.md` | Building and releasing the mobile app: build profiles and version numbers, permissions, the iOS privacy manifest, what the app collects for the store forms, universal and app links, the owner's steps once the store accounts exist, and store listing drafts. |
| `scripts/` | The load check, and backing up, restoring and checking a restored database, and exporting and replaying the deletion log. |
| `packages/api-client/` | TypeScript API client, generated from the service's own API description. |
| `packages/shared/` | Shared by web, mobile and the service: the wording, one file per language, and the list of supported languages. Also everything the two apps do that is not a screen: the calls to the API with their idempotency keys, the action runner, filling in wording messages, formatting dates, numbers and money, saving a working copy of terms and turning it into a revision, reading an invitation link. |
| `packages/shared/wording/privacy/`, `terms/` | The privacy policy's and the terms' text, one file per language ("Privacy policy and terms", below). |

The API description generated by the backend is the only thing that crosses the language boundary. Everything the product says lives in `packages/shared/wording`, one file per language; no user-facing text is written into a screen.

## Prerequisites

- Rust (stable) and Node.js with npm
- PostgreSQL 17, either through `docker compose up -d` or a local install
- For the mobile app: Xcode and/or Android Studio, or a device with a development build

## First run

```sh
cp .env.example .env
npm install

docker compose up -d                                         # database (or Homebrew, below)
cargo run --manifest-path backend/Cargo.toml --bin migrate   # apply migrations
cargo run --manifest-path backend/Cargo.toml --bin api       # http://127.0.0.1:8080

npm run dev:web                                              # http://localhost:5173
npm run dev:mobile
```

Without Docker, install PostgreSQL with Homebrew and create the two roles and the database that `.env.example` expects:

```sh
brew install postgresql@17 && brew services start postgresql@17
PG=/opt/homebrew/opt/postgresql@17/bin
$PG/psql -h 127.0.0.1 -d postgres \
  -c "CREATE ROLE exchange LOGIN CREATEDB PASSWORD 'exchange'" \
  -c "CREATE ROLE exchange_app LOGIN PASSWORD 'exchange_app'" \
  -c "CREATE DATABASE yuppers OWNER exchange"
```

The roles keep their technical names, `exchange` and `exchange_app`, because the migrations grant to `exchange_app` by name and an applied migration is never edited. `exchange` owns the schema and runs migrations; it may create databases because the API tests each build a throwaway one. `exchange_app` is what the API and worker connect as; it can add to the agreement history but not change or delete it.

A database created before the product was named Yuppers is called `exchange`. Either rename it once, with nothing connected to it, `$PG/psql -h 127.0.0.1 -d postgres -c "ALTER DATABASE exchange RENAME TO yuppers"` (in Docker: `docker compose exec postgres psql -U exchange -d postgres -c "ALTER DATABASE exchange RENAME TO yuppers"`), or keep pointing `DATABASE_URL` and `MIGRATION_DATABASE_URL` in your `.env` at `/exchange`. The roles need nothing.

In development, one-time codes are not sent anywhere: with `CODE_DELIVERY=log` the API writes each code to its own log, which is where you read it to sign in. Notifications work the same way: with `NOTIFICATION_DELIVERY=log` the worker writes each email to its log instead of sending it. Text messages and push notifications are off unless asked for; `SMS_CODE_DELIVERY=log` writes each code for a phone number to the API's log, number masked, where Twilio Verify would text it ("Signing in", below), `SMS_DELIVERY=log` writes each agreement update to the worker's ("Text updates", below), and `PUSH_DELIVERY=log` has the worker write each push notification to its log ("Notifications", below).

Every email goes as `multipart/alternative`: the plain text, then the same message as HTML (`backend/src/notifications/html.rs`), both made from the same wording in `packages/shared/wording`. The log shows the text and only the size of the HTML. To see the HTML, write every email in every language to a directory and open its `index.html` in a browser:

```sh
cd backend && cargo run --example email_preview -- /tmp/yuppers-emails
```

Each email is there as `<language>/<kind>.html`, with its text beside it as `.txt`. The values in them are made up, and nothing is sent. The HTML is a table layout with inline styles, no images, web fonts or scripts, and nothing fetched when it is opened; the mark is the blue `Y` tile drawn in text and colour. A browser shows roughly what a modern client does, not what every mail client does.

The API starts without a database: `/healthz` and `/v1/meta` respond, and `/readyz` returns 503 until PostgreSQL is reachable. The web dev server proxies API paths to the service, so the browser talks to one origin.

The web app signs in with a cookie, which the API honors only for requests from `WEB_ORIGIN`. If the dev server runs anywhere but `http://localhost:5173`, set `WEB_ORIGIN` in `.env` to match, or signing in will be refused. If the API listens anywhere but `127.0.0.1:8080`, tell the dev server where:

```sh
API_PROXY_TARGET=http://127.0.0.1:8084 npm run dev -w @yuppers/web -- --port 5184 --strictPort
```

On a physical device the mobile app cannot reach the development machine as `localhost`; set `EXPO_PUBLIC_API_URL` to the machine's LAN address.

The whole stack can also run in containers, built from the repository: `docker compose --profile full up --build` (with a `CONTACT_DATA_KEY` of your own in `.env`, as `docker-compose.yml` says) starts the database, applies the migrations, and runs the API serving the web app at `http://localhost:8080` and the worker, with codes and notifications in `docker compose logs api` and `docker compose logs worker`. See "Deploying" for what the image is.

## Mobile app

The app in `apps/mobile` takes an exchange from a draft to completion the way the web app does: sign in, profile, exchanges, composing and signing, invitations, and the exchange view, with an exchange's history and record, and report and block. Its screens are React Native components under `apps/mobile/src`; the routes are the files in `src/app`. What it knows about the API, the wording and the rules for a working copy comes from `packages/shared`, the same code the web app runs.

| Setting | What it is |
|---|---|
| `EXPO_PUBLIC_API_URL` | Where the service is. Defaults to `http://localhost:8080`. |
| `EXPO_PUBLIC_WEB_URL` | Where the web app is served from. Invitation links point there, `{web origin}/{language}/i#{token}`, so they work for someone without the app. Defaults to `http://localhost:5173`. When it is HTTPS, a build also claims its invitation links as universal and app links (below). |

- **Name and icons.** The app is Yuppers, with the iOS bundle identifier and Android package `app.yuppers` (`app.json`). Its icon (with iOS dark and tinted versions), the layers of the Android adaptive icon and the splash image are the Yuppers mark, two overlapping circles, drawn once in `scripts/make-icons.mjs`, which writes them all and the web favicon and touch icon too; run it again with `node apps/mobile/scripts/make-icons.mjs` (it needs `rsvg-convert`, from librsvg).
- **Session.** The app signs in for a token, keeps it in the device's secure storage through `expo-secure-store` and nowhere else, and sends it as a bearer token (`src/lib/session.ts`, `src/lib/token-store.ts`).
- **Builds.** `eas.json` has `development` (a development client, also as `development-simulator` for the iOS Simulator), `preview` and `production` profiles; the version people see is `version` in `app.json`, and EAS keeps the build number. `app.config.ts` starts from `app.json` and adds what depends on the build's environment. Nothing in the repository names an Expo project or owner yet: the owner runs `npx eas-cli@latest init` once, in `apps/mobile`, after creating the Expo account, and adds the project ID it prints to `app.json`. [docs/mobile-release.md](docs/mobile-release.md) has the steps, and the permissions, privacy manifest and store details.
- **Launch screen.** The Yuppers mark on the app's light or dark background, kept up until the app knows who is signed in, and four seconds at most (`src/lib/splash.ts`).
- **Invitation links.** An invitation reaches the app in three ways: as a universal link (iOS) or app link (Android), once the web domain names the app (`APPLE_APP_ID` and `ANDROID_SHA256_CERT_FINGERPRINTS` in "Deploying", and [docs/mobile-release.md](docs/mobile-release.md)); its own scheme, `yuppers://{language}/i#{token}`, and pasting the link into the app ("Open an invitation" on the first screen, signed in or not; signed out, it leads to signing in and then to the proposal, as the link does). Either way the token is taken out of the link before the router sees it and is held in memory only (`src/lib/invitation.ts`, `src/app/+native-intent.ts`). Links in notification emails, to an exchange (`{web origin}/exchanges/{id}`) or its record, are claimed the same way and open that exchange's screen.
- **Languages.** The device's language before sign-in and the account's after. Hermes, the engine the app runs on, has a narrower `Intl` than a browser: the shared formatting avoids what it lacks, and `src/lib/plural-rules.ts` supplies plural rules for every language from the Unicode data, so adding a language needs nothing in the app.
- **History and the record.** The exchange screen ends with its history, and `/exchanges/{id}/record` lays the whole record out to be read from top to bottom, by eye or with a screen reader, under the same plain summary as the web's (`src/screens/History.tsx`, `src/screens/RecordScreen.tsx`). A party takes their copy away through the system's share sheet, as a PDF or as the JSON document. For the PDF the record is laid out as one HTML page, summary first, with everything escaped and no script allowed (`src/lib/record-html.ts`), and `expo-print` prints it to a file. The share sheet takes a file, so either copy is written to the app's own cache first (`src/lib/record-sharer.ts`, with `expo-file-system`, `expo-print` and `expo-sharing`). There is never more than one such copy, and it goes when the next is made, when the account signs out, and on iOS as soon as the sheet closes.
- **Push notifications.** Offered only where they can arrive: on iOS or Android, in a build that names an Expo project (`eas init`), against a service that sends them (`push_notifications` in `GET /v1/meta`); otherwise the app says nothing about them. The system is asked for permission only when the person chooses to turn them on: from a card on the list of yups, which appears once they have a yup past its draft (sent, or joined), or from the switch on the account screen, which also follows the system's setting and leads to it when notifications are refused there. Never at the first launch, never before signing in. The device's Expo push token is registered with the service (`PUT /v1/me/devices`) and removed when the switch is turned off; signing out of the device removes it on the service. A tapped notification opens its exchange, whether it started the app or the app was running; one that arrives while the app is open is not shown (`src/lib/push.ts`, `src/components/Notifications.tsx`).
- **Wallet passes.** On an agreement in force, "Add to Apple Wallet" on iOS and "Add to Google Wallet" on Android, when the service issues passes for that wallet (`src/components/WalletButton.tsx`). On iOS the pass opens in Safari, which adds it to Wallet; the in-app sheet needs a native module the app does not have yet ([docs/wallet.md](docs/wallet.md)).
- **Report and block.** On the exchange screen once someone has joined, on the invitation screen once signed in to read the proposal (report only), and as a list of the people blocked on the account screen (`src/screens/ExchangeSafety.tsx`, `InvitationReport.tsx`, `BlockedPeople.tsx`). What is sent, and what the person is then told, is decided in `packages/shared` and is the same as on the web.
- **Tests.** `npm test -w @yuppers/mobile` runs every test twice, as an iOS build and as an Android build would load the app, including one that runs the whole app against a stand-in for the service. Native modules are mocked there; nothing replaces running it on devices before a release.

### Running the screens in a browser

The app's screens can be run in a browser with Expo's web target, to exercise them against a local API without a simulator. This is a test harness and nothing else: the web client people use is `apps/web`. Three files exist only for it and are bundled only for the web target: `src/lib/token-store.web.ts` (the session token in the tab's session storage, because secure storage has no web implementation), `src/components/DateField.web.tsx` (the browser's date input in place of the native picker) and `src/lib/record-sharer.web.ts` (a record's copy as a browser download, because a browser has no share sheet for a file; it shows what the copy holds and nothing about the sheet).

A browser will not call the API from another origin, and the service allows none, so a small proxy stands between them on the development machine:

```sh
cd apps/mobile
API_TARGET=http://127.0.0.1:8080 HARNESS_ORIGIN=http://localhost:8081 PORT=5185 node scripts/harness-proxy.mjs &
EXPO_PUBLIC_API_URL=http://localhost:5185 EXPO_PUBLIC_WEB_URL=http://localhost:8081 npx expo start --web
```

## Accessibility

Both apps are meant to be used with a screen reader, a keyboard or switch, text made much larger, and less motion, to WCAG 2.2 AA. What that means here:

- **Web.** One `main` and one `h1` per screen, headings in order below it, and a page title and `lang` that follow the screen and the chosen language. Every control has a label; a field that must be filled in says so (`aria-required`), and its error is tied to it (`aria-describedby`, `aria-invalid`) and the keyboard is taken to it. Panels that open in place take the focus and give it back to the button that opened them; there are no modal dialogs. What changes without the focus moving is said through two live regions that are always on the page (`src/lib/announce.ts`): polite for outcomes, assertive only for a refusal that stops the person. Text is at least 4.5:1 against its background and control edges and the focus ring 3:1, in light and dark; status is said in words, never by colour alone. The one thing that moves is the both-signed moment settling straight, once, and with `prefers-reduced-motion` it is shown still; the appearance follows the device unless the person chooses Light or Dark (account page, or Appearance in the footer); zoom is never blocked; targets are at least 44 CSS pixels tall.
- **Mobile.** Every pressable control and input has a role, a label and its state, with a hint where the label does not say enough; headings have the header role; targets are at least 48 points. Text follows the device's text size with no upper limit. The product's words are marked with their language for VoiceOver. What changes without the focus moving is said with `AccessibilityInfo.announceForAccessibility`; a panel takes the screen reader's focus and gives it back on cancel; screen transitions stop when the system asks for less motion.

How it is checked:

- `src/a11y.test.tsx` in `apps/web` runs the whole web app in jsdom against a stand-in for the service and checks the invitation page, sign-in, the composer, the exchange view, the record and the rest with [axe-core](https://github.com/dequelabs/axe-core) (WCAG 2.0 to 2.2 A and AA, and axe's best practices). Any violation fails `npm test`. It also checks where the focus goes, what is announced, and the page's title and language. `src/contrast.test.ts` computes the contrast of the colour pairs the stylesheet draws, which axe cannot do in jsdom.
- `npm run lint -w @yuppers/web` includes oxlint's `jsx-a11y` rules.
- `src/__tests__/accessibility.test.tsx` in `apps/mobile` walks the main screens, as iOS and as Android, and fails on any pressable control without a role, label, state or a 44-point target, any input without a label, or a screen without a heading; it also checks what is announced and that panels move the screen reader's focus.
- `e2e/narrow.spec.ts` in `apps/web` goes through the main screens in Spanish in a window 320 CSS pixels wide (WCAG 1.4.10, reflow) and fails if the page scrolls sideways or a button, link, tag, heading or field sticks out of the window or cuts its text off.

None of this replaces trying the apps with VoiceOver, TalkBack, NVDA and a keyboard, at the largest text sizes, before a release: the automated checks see the structure, not how it sounds or how it lays out.

### End-to-end tests

`apps/web/e2e` drives the built web app in Chromium with Playwright, against the real API and a real PostgreSQL database. Each test signs up its own people, each in a browser context of their own, with `example.test` addresses nobody else uses, so tests are independent and run in parallel. They go through the screens as a person would: a first proposal through to a completed exchange and its record, the record's plain summary and its print layout, counter-proposals, declining and withdrawing, discarding a draft, amendments, disputes, a close request, the guide for when something isn't working, what a proposal changes for the person asked to sign it, blocking, Spanish, the main screens in Spanish at 320 pixels wide, account deletion, a build the service says is too old, signing in with a phone number, which gets its code by text only once the box beside it is ticked, a replaced invitation link, an invitation link shared from a desktop browser (copied, its email, text message and WhatsApp addresses, and its QR code), a report reviewed by a reviewer named with the `staff` command (dismissed, and an account suspended and reinstated), the help pages, opened from the signing step and read through their contents, the privacy policy and the terms, read with scripts off as the service sends them, then as the app shows them, and opened from signing in, the page on how people opt in to texts with its steps on the website and in the mobile app and their pictures, turning on text updates for an agreement, with the confirmation shown and an update text queued once the other party acts, removing the phone number from an account that has both, and, signed in by phone, opening an invitation sent to the email address of another account, combining the two and landing in the invitation. An invitation link opened signed out shows the same sign-in page whether the link is live or dead, and the proposal only after signing in.

```sh
npx playwright install chromium                              # once
cargo run --manifest-path backend/Cargo.toml --bin migrate   # the database the API will use
npm run e2e                                                  # builds the API and the web app, then runs the tests
```

`npm run e2e` starts the API on `http://127.0.0.1:8090`, serving the built web app from the same origin (`WEB_DIR`), with its database from `.env` and `CODE_DELIVERY=log`; a test reads a one-time code back from the API's log, `apps/web/e2e/.output/api.log`, so no mail server is involved. Every browser connects from 127.0.0.1 and sign-in is limited per network address, so the API runs with that limit raised out of the way (`SIGN_IN_CODE_REQUESTS_PER_ADDRESS_PER_HOUR`, `signInLimits` in `apps/web/e2e/support/env.ts`); the limits per email address stay as they are, since every person has an address of their own. The test for a build that is too old starts a second API on port 8091 with `MIN_CLIENT_VERSION_WEB` above the web app's version. `E2E_PORT`, `E2E_OUTDATED_PORT`, `E2E_API_LOG`, `E2E_API_BIN`, `E2E_STAFF_BIN` (the `staff` command the review tests name a reviewer with, run with the database from `.env` or the environment) and `E2E_WEB_DIR` change those; if an API already answers on `E2E_PORT` it is used as it is, and `E2E_API_LOG` must then name its log. The report of the last run is in `apps/web/playwright-report`.

Nothing that takes days is tested: a proposal or an invitation expiring, a close request lapsing into a close as unresolved, an exchange closed for inactivity. Those are the worker's timers, and the backend's tests cover them.

### Mobile end-to-end tests

`apps/mobile/e2e` runs the mobile app's screens in Chromium the size of a phone (Playwright's iPhone 15), through the browser harness above, against the real API and a real PostgreSQL database. It is not a device run and does not replace one. As in the web suite, each test signs up its own people with `example.test` addresses and reads their codes from the API's log. The person under test uses the app; the other party acts through the API, as their own app would. The tests cover signing in and the profile, signing in with a phone number once the box beside it is ticked, opening an invitation link (from the link, or pasted in before signing in), signing up from it, then reading the terms with the notice that money is paid outside and accepting, reporting a proposal from its invitation once signed in, marking delivery and confirming it, the list with closed exchanges folded away, the history with its earlier entries, the record and its copy, report and block, deleting an account, removing the phone number from an account that has both, combining two accounts from an invitation sent to the other's email address, and Spanish.

```sh
npx playwright install chromium                              # once
cargo run --manifest-path backend/Cargo.toml --bin migrate   # the database the API will use
npm run e2e:mobile                                           # builds the API, exports the app for the web, runs the tests
```

`npm run e2e:mobile` exports the app with `npx expo export --platform web` into `apps/mobile/e2e/.output/web`, with the harness proxy's address built in. The tests then start three processes, unless one already answers: the API on `http://127.0.0.1:8103`, the harness proxy on `8203`, and a static server for the export on `5203`; `E2E_MOBILE_API_PORT`, `E2E_MOBILE_PROXY_PORT` and `E2E_MOBILE_WEB_PORT` change them, for the export too. The API's log is `apps/mobile/e2e/.output/api.log` (`E2E_MOBILE_API_LOG`), and the report of the last run is in `apps/mobile/playwright-report`. Every request comes from 127.0.0.1, so, as in the web suite, the API runs with its per-address sign-in limits raised out of the way.

What the harness cannot show, because it only exists on a device:

- **Secure storage.** In the browser the session token is kept in the tab's session storage (`token-store.web.ts`); keeping it in the keychain or keystore is not exercised.
- **The share sheet.** A record's copy becomes a browser download (`record-sharer.web.ts`). The tests check what the file holds, not the sheet, the copy in the app's cache, or its removal.
- **The PDF.** In the browser, "Save as PDF" opens the print window of the page shown; only a device prints the record's own page with `expo-print`. The jest tests check that page and what is handed to the sheet.
- **Links handed over by the system.** `+native-intent.ts`, which takes an invitation's token out of a link before the router sees it, runs only on a device; in the browser the tests open the link's own address, `/{language}/i#…`, which the app handles too.
- **The native date picker, the platform's switches and back gesture, screen reader announcements, larger text and less motion, and the narrower `Intl` of Hermes.** The browser has its own of each.
- **A build too old for the service.** The harness names no client version, so `CLIENT_TOO_OLD` is never reached.
- **Wallet buttons.** The harness is neither iOS nor Android, so it offers no wallet; the jest tests run the button as each, and nothing has added a pass to a real wallet ([docs/wallet.md](docs/wallet.md)).
- **Composing and sending terms in the app.** Not covered yet: in these tests the person who starts an exchange does it through the API.

## CI

GitHub Actions runs [`.github/workflows/ci.yml`](.github/workflows/ci.yml) on every pull request and on every push to `main`. A newer push to the same branch cancels the run in progress. Seven jobs run side by side:

- **Backend and API client**, against a PostgreSQL 17 container with the same two roles as local development: `cargo fmt --check`, `cargo clippy --all-targets` with warnings as errors, `cargo test`, and then `npm run gen:api`, which fails the job if it changes anything under `packages/api-client`. A stale client means the contract has drifted; regenerate it and commit the result.
- **TypeScript**: `npm ci`, `npm run typecheck` (which includes the wording and length checks), `npm run lint -w @yuppers/web` (warnings fail it), `npm run lint -w @yuppers/mobile`, `npm test`, `npm run build:web` and the invitation page's size budget.
- **Mobile app config**: `npx expo-doctor`, and the iOS and Android projects generated from the app config with `npx expo prebuild` into a directory that is thrown away, checked for the app links, the privacy manifest and the permissions removed ([docs/mobile-release.md](docs/mobile-release.md), "Checks in CI"). Nothing is built or signed, and no account is needed.
- **Container image**: checks `render.yaml` against Render's published Blueprint schema, builds the `Dockerfile` with the commit and build time, starts the whole stack from `docker-compose.yml` and checks it from outside: `/healthz` and `/readyz` answer, the web app's entry pages and the privacy policy's and the terms' pages are served in each language with the right cache and security headers, API paths keep precedence, a request ID comes back, `/v1/meta`, the `X-Yuppers-Version` header, the metrics and the worker's log name the commit the image was built from (and the web app was built with it), metrics answer on their own port and not on the public one, and the worker starts, reports its passes and exits cleanly when stopped. Docker is not needed on a development machine for anything else, so this job is where the image is verified.
- **End to end**: against a PostgreSQL 17 container, builds the API and the web app, applies the migrations, starts the API in the background and runs `apps/web/e2e` in Chromium. When it fails, the Playwright report, with a trace of each failed test, and the API's log are kept as the run's `playwright-report` artifact.
- **Mobile end to end**: the same, for `apps/mobile/e2e`: it exports the mobile app for the web instead of building the web app, and the tests start the harness proxy and a server for the export. Its report and the API's log are kept as `mobile-playwright-report` when it fails.
- **Backup and restore**: fills a database through the API with the load check, backs it up with `scripts/backup.sh`, restores it into a new database with `scripts/restore.sh` (which first has to refuse the non-empty source), and proves the copy is the same: `scripts/check-restore.sh` compares grants, triggers and every table's rows, `backend/tests/schema.rs` runs against the copy, and `scripts/check-restored-record.sh` reads a signed agreement back through the API with its hash intact. Then it deletes an account through the API, restores the earlier backup again, sees the account come back, replays a newer backup's deletion log with `scripts/replay-deletions.sh`, and checks the account is deleted again with its address free and its sessions gone. [docs/operations.md](docs/operations.md), "The restore drill", is the same by hand.

The workflow names the Rust and Node versions it uses; raise them there when the project moves to newer ones.

### Dependencies

[`.github/workflows/audit.yml`](.github/workflows/audit.yml) checks the locked dependencies against the published advisories every Monday and whenever it is started by hand (Actions, "Dependency audit", "Run workflow"): `npm audit --audit-level=high` and `cargo audit`. It fails on high or critical only, and never runs on a push or a pull request, since a new advisory says nothing about the change in front of you. An npm advisory that has been looked at and accepted is named in the workflow, so it does not fail every week; each is below, and comes off the list when its fix lands.

The base images in the `Dockerfile`, the PostgreSQL image in the workflows and every action are pinned by digest or commit, with the tag or version beside it. [`.github/dependabot.yml`](.github/dependabot.yml) proposes newer digests for the `Dockerfile` and the actions every week, as pull requests that CI checks like any other. ## Backend binaries

- `api` — the HTTP service. With `WEB_DIR` set, it also serves the built web app from the same origin: each language's entry page at `/{language}/i`, the app's own page for any other path the API does not route, and hashed assets cached for a year (`backend/src/http/web.rs`).
- `worker` — background jobs: expiries and closures on their timers, and reminders that something is due soon or overdue, and delivering notifications from the outbox.
- `migrate` — applies migrations as the schema owner. The API and worker never run them. With `MIGRATE_CREATE_APP_ROLE=true` it first creates the application role if it does not exist (`backend/src/app_role.rs`; README, "Deploying").
- `openapi` — prints the API description that the TypeScript client is generated from.
- `staff` — names who reviews abuse reports: `grant`, `revoke` and `list`, run by the owner with the schema owner's connection, never by the service ([docs/operations.md](docs/operations.md), "Reviewing reports").
- `replay-deletions` — after a restore, deletes again the accounts a deletion log names, through the service's own deletion ([docs/operations.md](docs/operations.md), "Replaying deletions").
- `contact-data` — `status` says how many encrypted email addresses, phone numbers and payment options are under which key; `rotate` re-encrypts them under a new `CONTACT_DATA_KEY`. Run by the owner with the schema owner's connection ("Contact details at rest", below; [docs/operations.md](docs/operations.md), "Contact data key").

Both long-running binaries stop cleanly on `Ctrl-C` and on `SIGTERM`, which is what a container runtime or service manager sends.

### Load check

`scripts/load-check.mjs` takes pairs of people through a whole exchange over HTTP against a running `api` and `worker`, many pairs at once. Each pair signs in with the codes the API writes to its log, gives names and confirms ages; the initiator saves a working copy and sends a revision with three contributions; the counterparty previews and claims the invitation and accepts; the initiator confirms them; each marks one contribution delivered and the other confirms it; the initiator proposes ending with the third outstanding and the counterparty agrees; and each reads the exchange, its history, its record and their list. It reports per endpoint the count, p50, p95 and p99 latency and errors, then the throughput, the API's peak resident memory, the connections and lock waits it saw in `pg_stat_activity` (sampled a few times a second, so a short wait can be missed), and how long the worker took to send the notifications the run queued.

Every person is a new account and every initiator makes one exchange, so the per-account limits are never approached: one code per email address against `codes_per_hour`, one exchange per initiator against `exchanges_per_day`, one invitation per exchange, and at most six changes by one party to one exchange in a minute against `changes_per_minute`. Code requests are also limited per network address, and the whole run comes from one machine, so the API under test is started with that limit raised out of the way (`SIGN_IN_CODE_REQUESTS_PER_ADDRESS_PER_HOUR=1000000`). Without that, every code request after the tenth in an hour is refused, and the script says why.

It writes agreement history, which cannot be deleted, so give it a database of its own. With `.env` pointing there and `CODE_DELIVERY=log`, `NOTIFICATION_DELIVERY=log`:

```sh
cargo build --release --manifest-path backend/Cargo.toml --bins
./backend/target/release/migrate
SIGN_IN_CODE_REQUESTS_PER_ADDRESS_PER_HOUR=1000000 ./backend/target/release/api > api.log 2>&1 &
./backend/target/release/worker > worker.log 2>&1 &
node scripts/load-check.mjs --pairs 200 --concurrency 25 --base-url http://127.0.0.1:8080 \
  --api-log api.log --database-url postgres://exchange:exchange@127.0.0.1:5432/yuppers_load
```

`--database-url` is only read from, for the connection and outbox figures; give the schema owner's, which sees every connection's state, and set `PSQL` if `psql` is not on the path. `--json` prints the report as JSON. The API's process is found by its port, or given with `--api-pid`.

On an Apple M4 with 10 cores and 16 GB, with PostgreSQL 17 on the same machine, release builds, in October 2026, against a database that already held 6,250 exchanges from earlier runs. Other agents were working on the machine at the same time (load average 2 to 6 across the runs), so take the figures as an order of magnitude.

| | 50 pairs, 10 at once | 200 pairs, 25 at once |
|---|---|---|
| Requests | 1,550 in 0.4 s, 3,470 a second | 6,200 in 1.2 s, 4,970 a second |
| Errors | none | none |
| Slowest p95 | 33 ms, creating an exchange (the first loads the list of timezones) | 15 ms, signing in |
| Every other p95 | 21 ms or less | 13 ms or less |
| API peak resident memory | 12.8 MB | 16.6 MB |
| Database connections, peak | 13 open, none waiting on a lock or idle in a transaction | 13 open, none waiting on a lock or idle in a transaction |
| Notifications queued, and sent | 500, all sent 4.5 s after the run | 2,000, all sent 3.8 s after the run |

The per-endpoint p95 at 200 pairs, in milliseconds: signing in 15.1, requesting a code 13.4, sending a revision 11.9, claiming 9.0, a command 8.6, the profile 8.0, creating an exchange 7.0, the record 6.8, reading an exchange 6.3, the list 5.0, saving a working copy 4.9, previewing 4.9, the history 4.7. The notifications are sent within a tick of five seconds, so the time to send them depends on where in the tick the run ends.

What the first runs found, and what was done:

- **Creating an exchange** was the slowest request by far (p95 199 ms at 25 at once). Checking the timezone read PostgreSQL's whole timezone database each time; the list is now read once per process.
- **The outbox** drained at one batch of 100 per five-second tick: 2,000 notifications took 94 s to send, though a batch took under 50 ms. The worker now goes round again at once after a full batch.
- **Three queries read the whole `exchange` table**: the per-account count on every creation and two of the worker's timers on every pass. Migration `0009_load_indexes` indexes them.
- **Nothing grew with the data.** After 4,000 more pairs (4,450 exchanges, 49,000 events), a 200-pair run's p50 for the list, the history and the record was within a millisecond of the run on an empty database (3.4, 3.8 and 6.2 ms), and their p95 within 8 ms, about the spread between two runs on this machine. Their plans, and the worker's, are index scans that read only the exchange or the rows asked for. No lock waits and no connection idle in a transaction were seen in any run, and the API's pool of 10 connections served 25 at once without an error.
- **One run stalled**: 200 pairs took 16 s, with every endpoint's p95 between 200 and 470 ms. It ran straight after the 4,000-pair fill, while autovacuum went through every table and other tests forced a checkpoint on the shared server, at a load average of 10. The six runs after it, two of them while the worker was sending a backlog of several thousand, were normal.

## Deploying

Nothing in the service assumes a particular host. A deployment is a PostgreSQL database, one container image (or the three binaries) and a handful of settings; `.env.example` documents every setting with its default, and the processes refuse to start without the required ones.

**On Render.** The first deployment is on Render: `render.yaml` is the Blueprint (the API serving the web app, the worker, PostgreSQL 17, migrations before each deploy), and [docs/deploy-render.md](docs/deploy-render.md) is the owner's checklist from creating the accounts to the first sign-in, with the email provider's DNS, backups, rollback and costs. CI checks `render.yaml` against Render's published schema.

**The image.** The `Dockerfile` builds the web app and the backend and produces one image on a distroless base (a libc and CA certificates, no shell) holding `api`, `worker` and `migrate` and the built web app under `/srv/web`. The default command is the API, listening on `0.0.0.0:8080` and serving the web app; the other two run by naming them (`docker run <image> /usr/local/bin/worker`, `/usr/local/bin/migrate`). The image contains no secrets and no configuration beyond those two defaults; everything else comes from the environment at run time. It does carry which build it is: the git commit and build time, given as the `GIT_SHA` and `BUILD_TIME` build arguments (CI passes them; on Render, `RENDER_GIT_COMMIT` stands in), which `GET /v1/meta` (`commit`, `built_at`), every response's `X-Yuppers-Version` header, each process's first log line and the `yuppers_build_info` metric report, and the web app shows on its account and staff screens ([docs/operations.md](docs/operations.md), "What is deployed"). A build without them still builds and says `unknown`. `docker-compose.yml` shows the three processes wired together with the database, and the container job in CI builds and smoke-tests the image on every change.

## Conventions

- **Rules live on the server.** Clients may check input shape; the service decides everything else.
- **State machines are pure functions** in `backend/src/domain`, tested against every row of the tables in `DESIGN.md` §5. `exchange.rs` is the entry point: `decide` takes an exchange, an actor, a command and the time, and returns events and the new state or a typed refusal.
- **Refusals are typed.** The API returns a stable `ErrorCode`; clients map it to wording. Adding a code in `backend/src/error.rs` and regenerating the client makes every language fail the wording check until it covers it.
- **Mobile dependencies** are added with `npx expo install <package>` from `apps/mobile`, which picks versions that match the Expo SDK.
- **One React version** across the repository, pinned to the one the Expo SDK uses.

## Guards on the wording and the invitation page

- **Text written into a screen.** `apps/web/src/pseudo.test.tsx` and `apps/mobile/src/__tests__/pseudo.test.tsx` run the main screens in a pseudo-language made from `en.json` at test time, every Latin letter accented and each message bracketed and a third longer (`Your terms` becomes `[Ýöûŕ ţéŕɱš····]`, placeholders kept), and fail on any plain Latin letter that did not come through it: in text, labels, hints, placeholders and, on mobile, the page the record's PDF is printed from. What may still have plain letters is listed in the tests and kept short: what people wrote or chose in the stand-in data, month names and other words the platform puts in a date, each language's own name and tag, and references, ids, hashes, email addresses and invitation links. The pseudo-language is `packages/shared/src/testing/pseudo.ts`, which nothing in the apps imports, so it is never built into them.
- **Lengths.** `packages/shared/scripts/check-lengths.mjs`, part of `npm run typecheck`, reports the messages whose translation runs much longer than the English, for information, and fails when a message in a tight space is longer than its group allows in any language: button labels, navigation and screen titles, status tags, and the lines of a card in the mobile list. The groups are listed by key at the top of the script; a new button or title goes into its group there. It also holds the store listing drafts in `docs/mobile-release.md` to the length each field names. Whether the screens really fit is `e2e/narrow.spec.ts` (Accessibility, above).
- **The invitation page's size.** `apps/web/scripts/check-budget.mjs` adds up, from the build's manifest, everything `/{language}/i` loads before anyone can act on it (the entry page, the entry script and the chunks it imports, the stylesheet, and the one language's wording) with gzip and with brotli, prints it per language with the main app's size for comparison, and fails when the largest language is over `apps/web/budget.json`. The two fonts the invitation page preloads (Instrument Sans 400 and Gabarito 900, `apps/web/build/font-preload.ts`) have a budget of their own there, in bytes as stored, since WOFF2 is already compressed. The web fonts are subset to Latin and the punctuation and symbols the wording uses (`apps/web/src/fonts/README.md`); `apps/web/build/fonts.test.ts` fails if the wording, the web app's text or a stylesheet's `content` uses a character a font lacks. The build writes the manifest to `apps/web/.build/`, outside what is served. The budget was set at the size in October 2026 plus about 10%. When it fails, find what grew first; raise the budget only if the invitation page needs it, in the same change, to the new size plus about 10%, saying why. The web app's copy of each language's wording leaves out what only the service sends, the emails and the text messages (`serviceWordingOut` in `apps/web/vite.config.ts`); the service and the mobile app read the files whole. The service compresses the web app's files itself (brotli or gzip, as the browser asks), so these are the sizes a phone receives; API responses are never compressed, because they carry personal data next to what a request sent.

## Adding a language

1. Add `packages/shared/wording/<code>.json` with every message that `en.json` has. The code is a language tag such as `fr` or `pt-BR`.
2. List it in `packages/shared/wording/languages.json`, with its own name for itself and its text direction.
3. Import it and add it to the `wording` object in `packages/shared/src/language.ts`.
4. Add `packages/shared/wording/help/<code>.json`, the help pages, with every piece that `help/en.json` has, and add it to `help` in `packages/shared/src/help.test.ts`.
5. Add `packages/shared/wording/privacy/<code>.json` and `terms/<code>.json`, the privacy policy and the terms, with every section and piece that the English files have, add them to `documents` in `packages/shared/src/legal.test.ts`, and add the language's required SMS wording to `apps/web/src/test/sms-requirements.ts`. The build writes their pages at `/<code>/privacy` and `/<code>/terms`.

`npm run typecheck` then fails until the file is complete, or while a button, title, status tag or mobile list line in it is longer than its space allows (below). The service reads the same list, so it needs no change, and neither does the API or the database. Nor does the mobile app. The web app needs none either: it finds the wording file by itself, and its build writes the language's invitation page, `/<code>/i`, from the file's `linkPreview` text. `DESIGN.md` §4.2 lists what else a language needs before it is offered to people, which is mostly not code.

## Help

The web app serves the help pages, open to anyone, signed in or not: `/help` lists the topics and `/help/{topic}` is one of them, with its sections listed at the top (`apps/web/src/screens/HelpPage.tsx`). The topics, in order, are in `HELP_TOPICS` (`packages/shared/src/help.ts`). A footer link on every web page leads there, and so does "Help" on the mobile account screen.

- **Text.** Each language's help is a file of its own, `packages/shared/wording/help/{language}.json`: per topic a title, a one-line summary and a list of headings, paragraphs and lists, in JSON so that the wording check covers it the way it covers the rest of the wording. It is apart from the product's wording file so that only the help pages load it: the invitation page's first load and the mobile app carry none of it, and the help page is a lazily loaded chunk of its own. Help says what the product does today; where it states a number of days, it names one of `HELP_FIGURES` as a placeholder, and `help.test.ts` fails if those differ from `Rules::default` in `backend/src/domain/mod.rs`.
- **"Learn more".** Small links from the places a topic explains: the signing step, the notice that money is paid outside, "Something isn't working", the amendment composer, the block panel, account deletion and the record (`HELP_LINKS`). On the web they open the topic in a new tab, so the step the person is in is not lost; in the app they open it in the system's browser (`apps/mobile/src/lib/help.ts`).
- **Language.** A help address may name its language, `/help/{topic}?lang=es`, which the web app shows the page in when nobody is signed in. The links from the apps always do, since the browser that opens them may not know the app's language.

## Privacy policy and terms

The privacy policy is at `/privacy` on the web app and the terms and conditions at `/terms`, and each at `/{language}/privacy` and `/{language}/terms` in every language but the default (`/es/privacy`, `/es/terms`). The policy says, in plain words, what the product collects and how it is used, who sees it, how long it is kept, what deleting an account does, and how to reach us (privacy@yuppers.app). The terms say what Yuppers is and is not, how it may be used, what review does, and the limits of what Yuppers.app promises (support@yuppers.app). Each has a section on text messages, `#text-messages`, which is what the SMS provider's review and the carriers ask for: it describes the one SMS program, the per-agreement updates a person may turn on ("Yuppers.app agreement updates"), with HELP and STOP in bold, and, under a heading of its own, one-time codes by text, which Twilio Verify sends and checks and which are not part of the program; and it links to the page on how people opt in, `/sms-opt-in` ("Text updates", below).

- **Text.** One file per document and language, `packages/shared/wording/{privacy,terms}/{language}.json`: sections under fixed anchors (`LEGAL_SECTIONS`, the same in every language), each a list of subheadings, paragraphs and lists. The wording check covers each document as a set of its own, so every language has the same sections and the same pieces in the same order. A message may name `{privacyEmail}` or `{supportEmail}`, which become `mailto:` links, a link to the other document (`{privacy}`, `{privacyTexts}`, `{terms}`, with the words in the document's `links`) or to the page on how people opt in to texts (`{smsOptIn}`, a whole page load, since the app has no page there), `{effectiveDate}`, and the figures in `LEGAL_FIGURES`, which `legal.test.ts` holds to the backend's own rules; text between `**` is strong. The two addresses and the effective dates are written once each, in `packages/shared/src/legal-text.ts`. `apps/web/src/test/sms-requirements.ts` holds the SMS registration's required wording, and both kinds of page are checked against it in both languages.
- **Two ways to read them, one text.** The web app's own page (`apps/web/src/screens/LegalPage.tsx`) is a lazily loaded chunk, with the text a file of its own per document and language, so the invitation page's first load does not carry it; it shows the document in the language on screen and keeps the address in step with it. The web build also writes a static page per document and language (`apps/web/build/legal-pages.ts`): the app's entry page, with the same script and stylesheet, and the document already written into `#root`, so the page reads in full with scripts off, for crawlers and reviewers, and with them the app draws the same document over it. The only inline script is the one every page has, which applies the appearance chosen on the device before the first paint and is allowed by its hash (`apps/web/build/theme-script.ts`), so the Content-Security-Policy is the same as every other page's. The service answers `/privacy`, `/terms` and their language versions with those files (`backend/src/http/web.rs`), without a redirect.
- **Links.** The web footer, beside Help; the sign-in form, with both documents and, where a phone number may be given, a link to the policy's section on texts (what texts cost and how to stop them is in the box beside a number, "Signing in"); the account page (both), and account deletion (to what deleting leaves); the help pages' list of topics (both). In the mobile app, the account screen, the sign-in screen and account deletion open the web pages in the browser, in the app's language (`apps/mobile/src/lib/legal.ts`). Links that leave a form open a new tab.
- **Keeping them true.** Both documents say what the code does today, and nothing it does not. **Any change to what is collected, kept, shown, shared or deleted, to a provider, a retention period or a setting the documents describe, or to how Yuppers may be used, changes the documents in the same pull request, with a new effective date in `LEGAL_EFFECTIVE_DATES`.** Places to check: the migrations, `backend/src/deletion.rs`, the worker's purges, the outbox, SMS, push and Wallet code, review (`backend/src/review.rs`), the logs, the cookies and browser storage, `render.yaml` and the providers in `docs/deploy-render.md`, and the store forms in `docs/mobile-release.md`. The opt-in box of agreement updates shows the consent wording the terms quote, word for word (`smsUpdates.consent`, held to the terms' quote in both languages by `packages/shared/src/sms-updates.test.ts`), and so does the box beside a number a code is texted to (`smsCode`, held to the terms' quote and to what the terms say the other two forms change by `packages/shared/src/sms-code-consent.test.ts`).

## An exchange's record

Each party can read everything an exchange holds and take a copy away (`DESIGN.md` §10, §14.1). Like the exchange itself, the record is visible only to its two parties, and it names them only as the agreement does: no email address, phone number or account ID is in it.

- `GET /v1/exchanges/{id}/history` is what happened, oldest first, with what the parties wrote along the way: the message sent with a revision, a note on a delivery, the reason for a dispute, a statement about closing. It answers with the latest 50 events (`limit`, at most 200) and says where the page before starts.
- `GET /v1/exchanges/{id}/record` is the copy: one self-contained JSON document (`format: "exchange-record"`, `format_version: 2`) with how the exchange stands, every revision sent and what became of it, every signature, and the whole history. It says in words, in the reader's language, what a signature rests on (one one-time code, nothing more), and that what the parties recorded about delivery is their own account and was not checked.
- Each revision in the copy carries `signed`, exactly what was signed, and `content_hash`. The hash is the SHA-256 of `signed` as canonical JSON (RFC 8785), so anyone holding the copy can recompute it; `backend/src/domain/canonical.rs` defines the format and `backend/tests/record.rs` recomputes it independently.
- One document holds at most 500 events, and at most 50 revisions or about a megabyte of their text. A longer record continues in further documents: `part.next` says where the next one starts and `part.complete` says when one document is all of it.
- Someone who opened the invitation and was removed before being confirmed (below) stays in the record without being named: what they did is marked `by_removed_claimant`, and a signature they left is listed apart, under `void_signatures`, never among `signatures`.

On the web, an exchange's page ends with its history, and `/exchanges/{id}/record` lays the whole record out for reading and printing, under a plain summary: who the parties are, what each agreed to give (or would have, if nothing was agreed), who signed and when, how it ended or where it stands, and what became of each item. The summary is worked out from the record document in `packages/shared/src/summary.ts`, so both apps say the same. "Save as PDF" opens the browser's print window, whose print rules leave out everything but the summary and the record, and a button downloads the JSON copy. The mobile app has the same summary, and hands its copy, a PDF or the JSON document, to the system's share sheet.

On an agreement in force, "Something isn't working" asks what the situation is (the other party hasn't done their part, I can't do mine, we both want to stop, we disagree whether something was done) and offers the existing actions that fit, each with what it means for who is released from what (`packages/shared/src/trouble.ts`). It sends nothing and adds no command: it opens the action's own panel. A dispute, opened or seen, says that the product records what each party says and does not decide who is right. The person asked to sign an amendment or a counteroffer sees, above the way to sign, what it changes field by field against the agreement in force or the version it answers, and for an amendment where each item will then stand (`packages/shared/src/changes.ts`).

## Passing an invitation on

Yuppers never sends an invitation itself, by design: sending to whatever address someone types would let it be used to spam or harass, and would wear down the sending domain's reputation. After signing, the initiator gets the invitation link, shown once, and passes it on through a channel of their own. The screen says so where the link appears ("Yuppers doesn't send this for you…"), with how to get a new link if it is lost.

- **Who it is for.** The composer expects the other person to be named: the email address or phone number the link is bound to is asked on its first page, beside their name, where it is thought of, saying why (only they can open it, and they can respond in full at once, with no confirming), that we do not contact them, and that they must sign in with exactly what is typed. A link for anyone is a deliberate choice offered after the field ("Make a link for anyone instead"), which says what it costs; an empty field is refused, never taken for one (`invitationForProblem`, `InvitationChoice`). The signing step names who it is for, or that it is for anyone, once more as part of what is about to be sent. It is checked before signing by the service's own rule (`boundToProblem` in `packages/shared/src/share.ts`): something plainly not an email address or phone number, a phone number where the service takes email addresses only (`sign_in_channels`; the field then asks for an email address only, as signing in does), and a phone number of a country it does not text are flagged under the field. The panel for a new link checks it the same way. The service holds the same line: the first proposal (`invitation`) and every new link (`POST /v1/exchanges/{id}/invitation`) must say either `bound_to` or `for_anyone: true`, and a request with neither or both is refused (`INVALID_REQUEST`), so a link for anyone is never what leaving something out gets.
- **"Share link".** Where the device has a share sheet (the web's `navigator.share`, when `navigator.canShare` takes the link; the apps' `Share.share`), it opens it, with "Copy link" and "Show QR code" beside it. Where it has none, as in most desktop browsers, it opens a panel in place: copy the link, an email (`mailto:`, addressed to whom the invitation is for when that is an email address), a text message (`sms:`, addressed to the phone number it is for), WhatsApp (`https://wa.me/?text=`), and the QR code. The message is "I've sent you a yup to review: {link}".
- **The token.** It stays in the link's fragment, which no server of ours sees. The email, text message and WhatsApp addresses carry the whole link percent-encoded inside their own text, and are opened by the device, never sent to this service. Whichever channel the person picks sees the link: sharing through WhatsApp means WhatsApp sees it, as with any other.
- **The QR code** is made on the device by [`lean-qr`](https://github.com/davidje13/lean-qr) (MIT, no dependencies) and drawn as an inline SVG on the web and as plain views in the app: nothing is fetched, so it works offline, and nothing is asked of the Content-Security-Policy. On the web the encoder is its own file (`apps/web/src/lib/qr.ts`, about 3.7 kB compressed), asked for when a link is shown and never by the page that first loads, so the invitation page does not carry it. Its Shift JIS mode is left out: `lean-qr` tries it with a `TextDecoder('sjis')`, which the app's runtime refuses.

## Reading an invitation

The proposal behind an invitation link is read signed in (`DESIGN.md` §9, §18 item 13a). Without a session, `POST /v1/invitations/preview` and `POST /v1/invitations/report` answer `401 UNAUTHENTICATED` for every token, live or dead, before the token is looked at; claiming already needed a session. With one, a dead link, a block between the reader and the sender, and a link that names someone else answer as they always have. So the only answers about a link come from an account, and an account that is blocked gets the dead-link answer from every endpoint: signed in or out, the blocked account has nothing to compare. `backend/tests/safety.rs` checks exactly that, endpoint by endpoint, against a made-up token. What is left is a second account: someone who signs up again with another email address or phone number and opens the same link sees the proposal there. That takes a second verified identifier, and the help on blocking says so.

The web page and the app's screen for a link show someone signed out only that a yup is waiting and the way to sign in, the same for every link; the link previews that messaging apps fetch stay generic (`linkPreview` in the wording). Signed in, the proposal is shown, with the way to report it; responding asks a new account for its name and age, then claims the invitation.

## Who opened the invitation

An invitation link that names nobody can be opened by whoever holds it, so the person who opens it is not yet a party (`DESIGN.md` §8). Until the initiator confirms them:

- They can read the proposal, sign it, and leave (`POST /v1/exchanges/{id}/leave`). Declining, proposing changes and everything else are refused with `AWAITING_CONFIRMATION`. A signature given now takes effect only when the initiator confirms.
- The initiator answers "is this who you invited?" with `CONFIRM_COUNTERPARTY` or `REJECT_COUNTERPARTY`. Rejecting removes them: the exchange no longer exists for them, anything they signed is void for good, and the proposal stays open for a new link (`POST /v1/exchanges/{id}/invitation`).
- Blocking the initiator from that position leaves the exchange too.

Someone the invitation named, or whom the initiator has confirmed, is a party and none of this applies to them. `backend/src/domain/exchange.rs` has the rules and `backend/tests/claimant.rs` runs them end to end; `backend/migrations/README.md` says how a signature stays tied to whoever held the place when it was made.

## A client that is too old

The web app and the mobile apps keep working against newer services until the service says otherwise. `GET /v1/meta` carries `minimum_client_versions`, the oldest build of each client (`web`, `ios`, `android`) that may still change anything; every client compares itself against it at startup and shows that it must be updated when it is below. Each request also names the client and its build in an `X-Client-Version` header, such as `ios/1.4.0` (the web app adds the commit it was built from, `web/0.1.0+abc1234`, which the comparison ignores as build metadata), and the service refuses a change from one below the minimum with `CLIENT_TOO_OLD`, leaving reading alone. The minimums are `MIN_CLIENT_VERSION_WEB`, `MIN_CLIENT_VERSION_IOS` and `MIN_CLIENT_VERSION_ANDROID` in the environment, dotted whole numbers; unset means no minimum, which is the default. `backend/src/client_version.rs` has the rule and `packages/shared/src/client-version.ts` the clients' copy of it.

A draft that was never sent can be thrown away from the composer. It goes through the rules like everything else, as `DISCARD`, and closes the exchange as `NOT_AGREED` with the reason `DISCARDED`, so it leaves the person's list and the record says what happened.

## Notifications

When one party does something in an exchange, or something is due soon or overdue, the other is told (`DESIGN.md` §12; which change tells whom is `backend/src/domain/notification.rs`). Each notice is queued in the outbox in the same transaction as its event, once per channel the person can be reached on, and the worker delivers it with retry (`backend/src/notifications/`).

- **Email, for everyone with an address**, as before, and whatever else happens: it says what kind of change it was and links to the exchange (and, for an agreement coming into force, to the record).
- **Push, as well, for anyone with the app on a device and notifications turned on there.** One notice per person: a person with a phone and a tablet gets it on both, and it is never sent twice to either (the outbox's key is one row per event, person and channel, and a notice the push service took for one device counts as sent). Push does not replace the email or wait for it. The design gives push to those who allowed it and email to everyone, and the two say different things: the push says only that a yup has an update, so the email remains the account of what happened. The cost is that someone with both gets two alerts for one change, one per channel, which is the design's rule; holding the email back while a push goes unread is a change the owner can choose later (`DESIGN.md` §18, item 15).
- **What a push says** is the same for every notice, in the recipient's language: "Your yup has an update." / "Tu yup tiene novedades." No exchange code, name, term or amount, because a lock screen is read by whoever holds the phone; the status detail the design allows as an opt-in is not built. Its payload is the exchange's path, `{"url": "/exchanges/{id}"}`, which the app opens after sign-in.
- **Text messages** carry one-time codes (made, sent and checked by Twilio Verify), and, to a party who turned them on for an agreement, one text per status change of it ("Text updates", below). An account with only a phone number gets no email, so push and those texts are the only ways it hears of a change: the account screen says so, and so does the help page on keeping track ("How we tell you").
- **Devices** are registered by the app under the session it is signed in with (`PUT /v1/me/devices`, `DELETE /v1/me/devices/{id}`, at most ten per account). Signing out of that session removes the device, as does deleting the account or the push service saying the token is no longer valid, at once or in a receipt read fifteen minutes later; one whose session expired gets nothing and is removed by the worker. A token registered by another account moves to it only once the session it was registered under has ended, or someone who learned another person's token could take their notifications; until then the registration is answered as usual and changes nothing, so the answer does not say whose the token is. A phone handed on without signing out keeps the first account's notifications until that session ends. Expo's tickets for receipts are removed after a day whether or not their receipts could be read.
- **Delivery** is chosen by the deployment and off until then: `PUSH_DELIVERY=log` writes each notification to the worker's log, `expo` sends through Expo's push service in batches of up to 100, with `EXPO_ACCESS_TOKEN` if the Expo project has push security on. Failures wait and retry like email (1 minute doubling to an hour, 8 tries). With push off, anything queued for push is closed unsent. The HTTPS client for Expo, Resend and the SMS provider is hyper with `hyper-rustls`, over the same rustls, ring and webpki roots that SMTP and the database use (`backend/src/outbound.rs`).
- **Not yet verified:** nothing has been sent through Expo, Apple, Google or Twilio; the requests are checked against stand-ins in `backend/tests/push.rs`, `backend/tests/sms.rs` and `backend/tests/verify.rs`, written from the providers' documentation. The design (§13.1) decides that app push goes straight from the backend to Apple's and Google's services with no third party; Expo's service is a third party, chosen here because it needs no Apple or Google credentials on the service and works the same for both platforms. The `PushSender` interface and the device table's `service` column leave room for direct adapters. That is the owner's call (docs/operations.md, "Decisions still open").

## Text updates

"Yuppers.app agreement updates", the one SMS program (`DESIGN.md` §12), sent through Twilio's Messages API under its own A2P 10DLC campaign (one-time codes go through Twilio Verify instead: "Signing in"): a party may turn on text updates for one agreement, and is then texted once per status change of it (`backend/src/notifications/sms_updates.rs`, `backend/src/http/sms.rs`, `packages/shared/src/sms-updates.ts`, and the "Text updates" control on the exchange screen of both apps).

- **Opting in.** On an agreement sent and not closed, "Text updates" shows, only while the service sends texts (`sms_updates` in `GET /v1/meta`). With no phone number on the account, the person first enters a US number, which gets a one-time code by text from Twilio Verify through the ordinary sign-in code (`POST /v1/auth/codes`) once the box beside it is ticked ("Signing in", the words `smsCode.verifyNumber`) and is added with it (`POST /v1/me/identifiers`), under the same limits and the `+1` rule. A sign-in code, not a code of a new purpose: adding an identifier has always proved it with a sign-in code, and a new purpose would need its own limits and checks for no gain, since the code proves the same thing, control of the number. Only the text that carries it is its own: "Yuppers.app: 123456 is your code to confirm this phone number. Do not share it with anyone." (`sms.verifyNumber`, "Signing in"). Then a box, unticked, beside the consent wording the terms quote word for word, its two addresses links, and Save (`PUT /v1/exchanges/{id}/sms-updates`). Saved ticked, the screen says "Text updates are on for this agreement. You'll get one text per status change at {number}. Reply STOP to opt out." (the number with all but its last four digits hidden), and the confirmation text is queued: "Yuppers.app: You're signed up for text updates about this agreement, one text per status change. Msg frequency varies. Msg & data rates may apply. Reply HELP for help, STOP to opt out." Saved unticked, they are off for that agreement.
- **What is stored** (migration 0020). `sms_update`: who turned updates on for which agreement, with which number. `sms_consent`, the record of consent, only ever added to: every opt-in (the account, the agreement, the number, the time, the consent wording's version, `SMS_CONSENT_VERSION`, and language, and which client) and every opt-out (by the person, by STOP, by a change of number, by deleting the account, by leaving or being removed from the agreement before being confirmed), and every STOP and START received. `sms_consent_network`: an opt-in's IP address and user agent, as for a signature, removed after the same 90 days. `sms_opt_out`: the numbers that replied STOP. The worker removes consent records four years after the updates they cover ended (`Rules::sms_consent_retention`, a placeholder for counsel): an opt-in four years after its updates were turned off, by whatever means, however old the opt-in itself; never one that updates still on, or a number still opted out, rest on. The privacy policy says so.
- **Sending.** The status changes the terms name, `Notice::texted_as_update` (a signature, a revision sent, an agreement or amendment in force, an item marked delivered, confirmed, disputed or waived, a request to close, and every closing), queue one `SMS` row in the outbox for each party told about it who has updates on, in the transaction of the event. The row holds only the kind of text and the notice. The worker writes the text when it sends it: "Yuppers.app: an agreement you turned on updates for has changed. See it: {link}. Reply STOP to opt out." (in Spanish "Yuppers.app: hubo un cambio en un acuerdo que sigues. Velo: {link}. Responde STOP para cancelar."), naming no term, amount, person or reference code. It sends only if the account still has the number updates were turned on with, the number has not replied STOP and its country is served. Update texts count under the hourly caps of codes, the whole service's and the one per prefix; past them a text waits for the next hour (and is dropped after a day). At most `SMS_UPDATES_PER_PERSON_PER_DAY` (default 20) are queued for one person a UTC day, confirmations included; past that, changes go by email and push only. With `SMS_DELIVERY=off` nothing is queued (the processes are told at start, `sms_updates::configure`), the control is hidden, turning updates on is refused, and the worker closes anything left queued.
- **Length.** In the GSM alphabet, so 160 characters a segment (153 when split). With the live origin an update is 163 characters in English, two segments, as the owner wrote it, and 156 in Spanish, one; the confirmation is two in both (184 and 231). The tests hold each to its count.
- **STOP, START and HELP.** Twilio posts every text sent to the number to `POST /v1/sms/inbound`. The service takes a request only with Twilio's `X-Twilio-Signature`, HMAC-SHA1 under the account's auth token of the URL Twilio requested (`WEB_ORIGIN` and the path) and the posted parameters sorted by name, compared in constant time; anything else gets 403. The route reads at most 32 KB (413 past it), and a request with more than 100 parameters, or a signature header that is not base64 for 20 bytes, is refused before its body is parsed; a refused signature is logged at most once a minute. Each STOP or START is remembered by its `MessageSid` for 30 days (`sms_inbound_seen`, migration 0023), and one already taken is answered the same but changes nothing, so neither Twilio's retries nor a captured START replayed after a later STOP undo anything. It answers at once with an empty TwiML document, so it never replies itself: Twilio's Advanced Opt-Out sends the HELP and STOP replies (docs/deploy-render.md, "Text messages"). A stop keyword (STOP, STOPALL, UNSUBSCRIBE, CANCEL, END, QUIT, OPTOUT, REVOKE, or Twilio's own `OptOutType`) puts the number on `sms_opt_out`, turns off every agreement's updates for it and records it all; from then on nothing is texted to it, and a code for it is refused with `PHONE_OPTED_OUT`, which the apps answer by pointing to email sign-in. START, UNSTOP or YES takes it off the list, and turns no agreement's updates back on.
- **Deleting an account** turns off its updates, recording each, and removes its number with everything else (`backend/src/deletion.rs`); the consent records stay, as the privacy policy says. Replacing the account's number turns off the updates that went to the old one.

## Payment options

Optional links to pay in another app, on a money item (`DESIGN.md` §7; `backend/src/payments.rs`, `backend/src/http/payments.rs`, `packages/shared/src/payments.ts`). Yuppers still moves no money and records a payment only as before: the payer says "I've paid" and the payee confirms receiving it. Nothing is recorded, or inferred, from a link being opened.

- **Saving them.** On their own screen in both apps (`/account/payments`, opened from one row on the account screen that names the apps added, or "None added"), a person may add any of a Venmo username (5 to 30 letters, digits, `-` or `_`; a leading `@` is dropped), a Cash App $Cashtag (1 to 20 letters, digits or `_`, with a letter; a leading `$` is dropped), a PayPal.Me name (1 to 20 letters or digits; `paypal.me/name` is read as the name) and, for Zelle, an email address or a US phone number. All are optional. The screen lists those added, each with Edit and Remove; "Add a payment option" asks which app, from those not added yet, then shows its one field. Removing asks first, in a dialog on the page, and says when it is the last one. Each is saved or removed on its own (`PUT`, `DELETE /v1/me/payment-handles/{kind}`, `kind` one of `venmo`, `cash_app`, `paypal`, `zelle`), which writes only its own column: the others keep their values and when they changed, two devices changing different ones never undo each other, and a refusal leaves the rest as they were. `GET /v1/me/payment-handles` reads them all; the whole-set `PUT` (one left out is removed) and `DELETE` (all of them) stay for builds that still send them. Both apps check the same rules before sending, and the service again (`INVALID_REQUEST`). They are stored encrypted like contact details ("Contact details at rest"), one column each, under `CONTACT_DATA_KEY` with the table and column as associated data, and also bound to the account whose row holds them, so a ciphertext copied into another account's row does not decrypt: it is left out, as if there were none, and an error naming only the column is logged. `contact-data rotate` re-encrypts them with the same binding (migration 0026).
- **Showing them on a yup.** Per party and per yup, off unless turned on (`PUT /v1/exchanges/{id}/payment-options`, `payment_offer`): a switch "Show my payment options on this yup" on the yup's page, for a party who receives money in the terms on the table or in force, and the same switch beside signing or sending such terms, which sets it once the signature has gone. It is not part of the terms: not in a revision, its content hash or the history, and it changes no version. It needs something saved to turn on, and works only while the yup is sent and not closed; turning it off always works. Removing every saved option turns it off on every yup, so options saved again later are shown nowhere until the person says so.
- **What the payer sees.** The exchange view carries `payment_options`: `shown` (whether the viewer shows theirs) and `theirs`, the other party's options decrypted for this view, only while they show them here, their account is active, nothing a reviewer hid applies, and the viewer owes them money on the agreement in force that is still to be paid (pending, or disputed back). On such an item the payer sees "Pay {name} {amount}", which opens a modal sheet: "Added by {name}. Yuppers doesn't check it or move money. Make sure it's the right person.", that the money is paid outside the service, that the app's own terms and fees apply, the amount and the note (`{item} · yup {reference}`) each with Copy, and one text-only button per app (no logos): `https://venmo.com/u/<username>?txn=pay&amount=<amount>&note=<note>`, `https://cash.app/$<cashtag>/<amount>` and `https://www.paypal.me/<name>/<amount>USD`, which each app's domain claims for its app (universal links on iOS, app links on Android), so the app opens where it is installed and its website otherwise. The web opens them in a new tab; the app with `Linking.openURL`, no custom scheme and no `LSApplicationQueriesSchemes`. The amount goes in a link only in US dollars; otherwise the sheet says to enter it. Zelle has no links: its address or number is shown with Copy. When an option changed after the agreement came into force, however long ago, the sheet says so in an alert just before its button: "{name} changed this Venmo username on {date}. Check with {name} another way before you pay." (`theirs_changed` in the view, with when each changed; `payment_handle.*_changed_at`, set when a value is set to one it did not have, including after being removed). One saved before the agreement came into force is not warned about. The old value is never kept or shown. The sheet reads the exchange again as it opens, so options turned off are not offered, and the exchange screens notice a change of `payment_options` when they check for updates even though the version is the same. "I've paid" in the sheet opens the usual claim, which the payer sends.
- **Never elsewhere.** Not in an email, a text, a push notification, a Wallet pass, a link preview, the record or a log (`backend/tests/payments.rs`, `contact_scan.rs`, `telemetry.rs`). Writes count against `payments::WRITES_PER_HOUR` (30) per account, refused with `TOO_MANY_REQUESTS`. Deleting the account removes them and every yup they were shown on; someone removed from a yup before being confirmed stops showing them there.

## Signing in

A one-time code is sent to an email address or phone number (`POST /v1/auth/codes`) and entered to sign in (`POST /v1/auth/sessions`). While a code by email is on its way, both apps say to look in the spam folder too, for an email from the address `GET /v1/meta` names in `code_sender` (the address part of `EMAIL_FROM`, or `SMTP_FROM`, without its display name; absent with `CODE_DELIVERY=log`), and offer "Send another code" only 30 seconds after the last one was sent, so a slow email does not use up the hourly limits below. A code for an email address goes by email. One for a phone number goes, with `SMS_CODE_DELIVERY=verify`, through **Twilio Verify** (`backend/src/notifications/verify.rs`): the service asks Verify to start a verification (`POST https://verify.twilio.com/v2/Services/{sid}/Verifications`, `To`, `Channel=sms`, `Locale` `en` or `es`), and Verify makes the code and texts it, from Twilio's own registered senders, in its own template with the service's friendly name, "Your Yuppers verification code is: 123456" in English and Twilio's own translation in Spanish; a code offered back is put to Verify (`.../VerificationCheck`, `To`, `Code`), whose `approved` is the only yes ([Verifications](https://www.twilio.com/docs/verify/api/verification), [VerificationCheck](https://www.twilio.com/docs/verify/api/verification-check)). These texts are not part of the agreement-updates program and need no campaign of ours. Verify sends one number the same code for every request within its ten minutes, so each purpose has a service of its own: `TWILIO_VERIFY_SERVICE_SID` for signing in and for a number being added to an account (a sign-in code, as it always was; the consent record says `VERIFY_NUMBER`), `TWILIO_VERIFY_DELETION_SERVICE_SID` for deleting an account. The service still records each code asked for, in `one_time_code` (migration 0022: `checked_by` `TWILIO_VERIFY`, no hash), so every limit below counts it as before; Verify is asked about a code only while such a request for that number and purpose is live, after the day's wrong guesses are checked, and a code Verify does not approve is charged as a wrong code exactly as one of the service's own. While Verify is asked, no database connection is held: a place in the day's wrong guesses is taken and committed first and given back once Verify answers (then a wrong code is counted as any is), so no more guesses can be with Verify at once than the day has left, and guesses for one number take turns within each copy of the API. A request Verify resends works only until the first one it resends expires, as Verify's code does. Once Verify approves a code, its keyed hash is written to the live requests, so that the same code works again until it is used or expires (Verify forgets an approved verification, and a deletion that found the account busy is tried again with the same code). A check Verify cannot answer is refused as `SERVICE_UNAVAILABLE` and charged to nobody. Email codes are made, hashed and checked by the service as before. With `SMS_CODE_DELIVERY=log`, for development, the service makes a phone code itself and writes it to the API's log, the number masked, counted as a text. While `SMS_CODE_DELIVERY` is off, a code for a phone number is refused as `SERVICE_UNAVAILABLE` where codes go by email (`CODE_DELIVERY=resend` or `smtp`), and written to the log in development (`CODE_DELIVERY=log`), as before; `SMS_DELIVERY`, which sends agreement updates, has no part in it. So phone sign-in depends on the deployment, and `GET /v1/meta` says which kinds of identifier it can send codes to now (`sign_in_channels`: `email`, and `phone` while `SMS_CODE_DELIVERY` is on or codes go to the log) and, with phone, the country codes taken (`sms_country_codes`). The sign-in screens of both apps ask for an email address only until the service offers phone numbers, and say "Sign in with your email address" to a phone number typed anyway, before anything is sent; with phone numbers offered they say US numbers only where `+1` is all that is taken (the default), and name the country codes otherwise. A US number is typed as people there write it, `(856) 548-8780`, `856-548-8780` or `8565488780`, with or without `1` or `+1` in front; both apps (`packages/shared/src/phone.ts`) and the service (`Identifier::parse`) read it as `+18565488780`, so what is stored and indexed is E.164 however it was typed, and the apps show it as `(856) 548-8780`, or `(•••) •••-8780` where it is partly hidden. Without a country code, the area code and the exchange must each begin with 2 to 9; a number with another country code is refused as `PHONE_COUNTRY_NOT_SERVED`, as before. Deleting an account then sends its code by email too, unless the account has only a phone number. Only phone numbers of the countries in `SMS_ALLOWED_COUNTRY_CODES` are taken (default `+1`; a comma-separated list such as `+1,+52`): a code for any other number, a deletion code to one, and adding one to an account are refused with `PHONE_COUNTRY_NOT_SERVED` before anything is counted or sent, so numbers the service would never text cannot use up anyone's limits. `+1` is the whole North American Numbering Plan, Canada and some twenty Caribbean and Pacific countries besides the US, so a `+1` number is taken only from the parts in `SMS_ALLOWED_REGIONS`, by area code (`backend/src/nanp.rs`): `US` by default, the 50 states and DC, or `US,CA`; the Caribbean and Pacific countries, the US territories and toll-free numbers never. The same check holds for agreement updates. The SMS provider's geographic permissions, set to match, are the second check (docs/operations.md). Text messages cost money, so besides the limits below the whole service sends at most `SMS_MAX_PER_HOUR` an hour (default 50), and at most `SMS_MAX_PER_PREFIX_PER_HOUR` (default 10) to numbers beginning alike (the country code and the next three digits: the area code for `+1`), and past either refuses codes for those phone numbers with `TOO_MANY_REQUESTS` until the hour turns. A place under both caps is taken before the message is handed to the provider and given back if the provider refuses it, so refused messages (a number that does not exist, a country outside the provider's permissions) use up nothing, while the caps still hold exactly; the counts are kept in the database, so they hold across copies of the API. The cap per prefix means that whoever sends codes to numbers that are not theirs turns off phone sign-in for one area code at a time, not for everyone at once. Phone numbers are masked in every log, the development delivery's included (`+1••••••••67`). The worker removes each code's row a day after it was asked for, once it has expired or been used (`SPENT_CODE_RETENTION`), so `one_time_code` holds an email address or phone number for about a day (the worker's next pass after the day is up). Asking again does not end the codes already sent: the newest three stay live until each expires, any of them works, and using one uses them all. Wrong codes are limited per code (5) and per email address or phone number per UTC day (20, after which even the right code is refused with `TOO_MANY_GUESSES` until the day ends, and no new code is sent); codes asked for, per email address or phone number (5) and per requester (10) per hour. Those are what bound guessing: a code takes five wrong guesses before it dies, an email address or phone number twenty a day, and every code guessed at must first be asked for, which the requester's hourly limit counts. A wrong code, an expired one and one already used all get the same `INVALID_CODE`, whether or not anyone asked for a code for that email address or phone number, so the answer never says that someone is signing in. Wrong codes are deliberately not limited per requester: past such a limit the service could only answer a wrong code differently where a code is live, which would say exactly that, or refuse right codes too, which would let one person lock out everyone sharing an address (an office, a mobile carrier). The requester is the network address that `TRUSTED_PROXY_HEADER` names, or else the connection's peer; an IPv6 requester is counted by its /64, and an IPv4 address written as IPv6 as the IPv4 address. Deletion codes are counted apart, against the account (5 an hour, 20 wrong a day), so nobody without the account's session can stop its owner from deleting it. A deletion code is not sent while the account has used up its wrong deletion guesses for the day (`TOO_MANY_GUESSES`, as for signing in). Every number is a placeholder in `AuthRules` (`backend/src/auth.rs`); the limit on codes asked for by requester and the daily limit on wrong codes by email address or phone number can be set by a deployment ("Deploying").

**Consent to a code by text** (`backend/src/code_consent.rs`, `packages/shared/src/sms-code-consent.ts`). Every form that texts a code shows, beside the number, a box that is never ticked to begin with and never remembered: sign-in as soon as what is typed reads as a phone number, account deletion when the code is to go to the phone, and the number added in "Text updates". Its words say what is sent, how often, the rates, HELP and STOP, and both policies' addresses as links that open a new tab (`smsCode` in the wording files; the terms quote the sign-in form's word for word, and say what the other two change). The button that sends the code stays disabled until the box is ticked, and says why, beside it and in its accessible description. Ticked, the request names the wording shown, `sms_consent: { version, language }`, where `version` is `CODE_CONSENT_VERSION` (`2026-10-06`), kept in step with `SMS_CODE_CONSENT_VERSION` by a test. `POST /v1/auth/codes` and `POST /v1/me/deletion/codes` refuse a code for a phone number without it, or with a version the service does not know, as `SMS_CONSENT_REQUIRED` (422), before anything is counted or sent and after the country check; a number that replied STOP is refused with `PHONE_OPTED_OUT` only after that, and once the request has been counted against the requester, so asking cannot list such numbers without limit; email addresses need none and the field is ignored for them. A client from before the box gets that refusal for every phone number, which the apps that know it explain. Each code issued after a tick is recorded with it, in the transaction that stores the code (`sms_code_consent`, migration 0021): why (`SIGN_IN`, `DELETE_ACCOUNT`, or `VERIFY_NUMBER` when a signed-in account asks, which is only ever "Text updates" adding a number), the account where there is one, the wording's version and language, the client (`X-Client-Version`) and the time, with the request's IP address and user agent apart (`sms_code_consent_network`), removed after 90 days as a signature's are. The number is kept in full only where it is already the account's own; otherwise only as `phone_hash`, an HMAC-SHA256 of it under `APP_SECRET`, which every record also has: anyone can type any number, and a record of a number nobody has shown is theirs should not hold it, but a complaint about a text names the number, and the hash finds the record from it. The worker removes the records after `Rules::sms_consent_retention` (four years); deleting an account leaves them, as the privacy policy says. Rotating `APP_SECRET` makes the hashes of earlier records unmatchable.

**Staying signed in** (`backend/src/http/extract.rs`). A session, the web app's cookie or the mobile app's bearer token alike, lasts as long as it is used at least once every `session_idle` (30 days), up to `session_max` (180 days) after the code that made it; then a new code is needed. The check that finds a session also renews it, in one statement: when less than a day short of the idle time is left, `expires_at` moves to `min(now + idle, created_at + max)`, so a session in constant use is written about once a day, not on every request. The web app's cookie is sent again with a `Max-Age` of what the session now has left whenever that happens, so the browser never drops it first; a response that clears the cookie (signing out, deleting the account) is left as it is. Only `expires_at` moves: `authenticated_at`, when the holder last entered a code, is what signing and the staff endpoints check for being recent, and a renewal leaves it alone. Signing out, a suspension and deleting the account end sessions as before. `SESSION_IDLE_DAYS` and `SESSION_MAX_DAYS` set the two lengths ("Deploying").

## Deleting an account

A person can delete their account from the account screen of the web app and of the mobile app (`DESIGN.md` §4.1), and from the profile step of an account that was never set up. `backend/src/deletion.rs` says in full what deleting does and why; `backend/tests/deletion.rs` checks each part against a real database.

- **Proof.** A session is not enough. `POST /v1/me/deletion/codes` sends a one-time code to the account's own email address or phone number (by text only once the box beside the number is ticked, "Signing in"), and `POST /v1/me/deletion` takes it. A code sent for deleting cannot sign in, and a sign-in code cannot delete. The code is used up only together with the deletion: if the account is busy and the deletion gives up (`SERVICE_UNAVAILABLE`), the same code works for another try, while a wrong code is counted against the account at once as always. `GET /v1/me/deletion` says beforehand what would happen to the exchanges the account is in.
- **The account.** Every session ends, on every device. The row stays, marked deleted, without its email address, phone number, name or language, so the same address can sign up again as a new account that sees nothing of the old one. Its working data goes with it: codes, the devices registered for its push notifications, unsent working copies, idempotency keys, queued notifications, the blocks it made, and invitation links nobody took.
- **Its exchanges.** Whatever happens to one happens through the rules, as commands in the departing party's name. A proposal still waiting to be signed is withdrawn or declined, which ends a negotiation with nothing agreed. Someone who had only opened an invitation and not yet been confirmed leaves the exchange instead, and the proposal stays open (above). An agreement in force gets a request to close, and the worker closes it as unresolved when the time to respond runs out; nothing is waived or accepted for the person leaving. Closed exchanges are not touched. While an exchange is still open, the other party's view of it says that the other party has left (`other_party_left`).
- **The deletion log.** The same transaction records the account's ID and the time, and nothing else, in `deletion_log`. A backup restored later would bring the account back; replaying the log deletes it again, through the same code, lifting first a suspension the restored copy still has, as the owner's in the review history (docs/operations.md, "Replaying deletions").
- **What it leaves alone.** Revisions, signatures and events. The other party keeps the exchange and its record, with the names as the agreement wrote them. What becomes of a departed person's words in that history is not decided by this code.

## Email address and phone number

The account screens of both apps show the account's email address and phone number, each with Add or Change and Remove (`packages/shared/src/identifiers.ts`, `Identifiers.tsx` in each app).

- **Adding and changing** take more than a session, as removing does: a stolen session must not add a way in, and then use it to take the owner's away. First a proof that the person controls one the account already has (when changing, the one being replaced or the other): `POST /v1/auth/codes` sends a code to it, and `POST /v1/me/identifiers/proof` (`channel` `EMAIL` or `PHONE`, `code`) turns that code into a proof, kept as its hash in `account_proof`, good once, for 10 minutes, for this account and only while it still has the identifier proved. Then `POST /v1/auth/codes` for the new one and `POST /v1/me/identifiers` with its code and `proof` add it, or replace the one of its kind. Without a good proof the answer is `PROOF_REQUIRED`, asked before the new code is looked at, so the code is not spent. One email address and one phone number per account. Adding a number from an agreement's "Text updates" sends the code to the account's email address with the one by text, and asks for both.
- **A day's grace.** The database records when each identifier came to the account (`email_added_at`, `phone_added_at`, stamped whenever the index changes). For `FRESH_IDENTIFIER` (24 hours, `backend/src/combine.rs`) a proof from a newer one, or a removal code sent to it, does not remove or replace one the account had before it (`IDENTIFIER_TOO_RECENT`): should a way in ever be added without the owner, the owner, told by email, has a day before it can take theirs. A new number ends the text updates of the old one, as before. The address replaced is emailed that it was (`EMAIL_CHANGED`), in the account's language; a number replaced is not texted, and the app shows the notice instead (`notice` in `GET /v1/me`, `PHONE_CHANGED`).
- **Removing** is `DELETE /v1/me/identifiers/{email|phone}` with a code sent to the other one, which stays (asked for with `POST /v1/auth/codes`, by text once the box beside the number is ticked). The only one is refused with `LAST_IDENTIFIER`, and the screens do not offer it, saying why. Removing the phone number ends every agreement's text updates, recorded as `PHONE_REMOVED`. The address removed is emailed that it was (`EMAIL_REMOVED`); a number removed is shown in the app (`PHONE_REMOVED`). Invitations sent to the address or number removed are left as they are. A repeat, with the same `Idempotency-Key` or after the removal, changes nothing and succeeds.
- **Notices in the app** (`notice` in `GET /v1/me`: `kind`, `ACCOUNTS_COMBINED`, `PHONE_CHANGED` or `PHONE_REMOVED`, and `at`) are what the account is told where there is no email address to tell. Both apps show one once, at the top of the list of yups, until "Got it" dismisses it (`PATCH /v1/me`, `dismiss_notice`). A newer one replaces an older.

## Combining accounts

Someone with two accounts, one signed in by email and one by phone, say, can make them one (`backend/src/combine.rs`, migration 0028, `backend/tests/combine.rs`).

- **The trigger.** Signed in to account A, the person adds an address or number that belongs to account B and enters the code sent to it. Until the code is right, nothing differs from adding any address, so nothing says whether one has an account. Then, instead of a refusal, the answer is `IDENTIFIER_ON_OTHER_ACCOUNT` (409) with `combine`: what B holds (its name, its address and number masked, its yups by state, whether it has payment options, text updates and devices), what combining would do to each kind of identifier, whether it needs a proof of A's own (`proof_required`, below), and a token. The token is kept as its hash in `account_combine_offer`, bound to A, B and the identifier proved (its blind index), and good once, for 10 minutes, from A only.
- **Refused**, with a code of its own for each: either account suspended (`COMBINE_SUSPENDED`), B a reviewer (`COMBINE_REVIEWER`), or A and B both parties to one yup, on its two sides or one as the other's unconfirmed claimant (`COMBINE_SHARED_EXCHANGE`). An offer used, expired, made for someone else, or no longer true (the address has since left B) is `COMBINE_EXPIRED`.
- **Combining** is `POST /v1/me/combine` with the token and an `Idempotency-Key`. It also takes `proof`, a proof of one of A's own ("Email address and phone number"), as adding or changing one directly does, since B's address or number comes to A whether or not it replaces A's own (`proof_required` in the offer); without a good one it is `PROOF_REQUIRED` (or `IDENTIFIER_TOO_RECENT`) and nothing happens. A proof given with the `POST /v1/me/identifiers` that found B is not used up by it, and serves here. Both account rows are held in a fixed order, then B's yups; the rows are taken outright only where their addresses change, without waiting, and the whole is tried again if one is busy, as a deletion does. In one transaction:
  - B's places in its yups pass to A. The database allows this one change of `participant.account_id` from an account to another, and only to the account the first is marked `MERGED` into; it ends B's holding as combined and opens one for A. What B signed and did stays as written, under B (append-only history); a signature B gave still counts while the chain of combined holdings reaches the place's current holding (`holding_void_since`), so an offer B signed before can still come into force. The record and its PDF show the names the agreement wrote, as before. Invitation links B took (`claimed_by`), B's unsent working copies and B's Wallet passes go to A; so does content a reviewer hid from B.
  - The address or number proved moves to A, replacing A's own of that kind. B's other one moves too if A has none of that kind; otherwise A keeps its own and B's is dropped. Account addresses are encrypted with their column as associated data, so the ciphertext moves as it is. A keeps its name and age confirmation, taking B's only where it has none.
  - Text updates: B's move with B's number, or end (`ACCOUNTS_COMBINED`) when B's number is dropped; A's end if A's number is replaced. `sms_consent` is never rewritten: its retention finds B's opt-ins through `merged_into`.
  - Payment options: A keeps its own, and B's are dropped with showing them. If A has none, B's are encrypted again for A (they are bound to their account) and marked changed now, so whoever owes money on B's agreements is warned that they changed.
  - Blocks between A and B are dropped. Every other block B made, or that was made against B, becomes A's, ending what was waiting to be signed between the two people in the blocker's name, as a new block does.
  - Notifications still waiting for B go to A: they are about yups that are A's now. B's sessions are revoked and its devices forgotten (a device is registered under a session; a signed-out device gets no pushes). Rate-limit counts stay. Reports and the review history stay under B.
  - B becomes `MERGED`: no address, number or name, `merged_into` A, `merged_at`; nobody can sign in to it. Accounts combined into B before now point at A, so `merged_into` is always one step. `account_merge` records it (append-only), before any place moves, and `deletion_log` gets B's line with `merged_into` and `merged_by`. The database holds the service to this: a place passes only by a combination `account_merge` records, `MERGED` is never taken back, and `merged_into` changes only to follow a later combination of the account it points at.
  - Every email address either account had is emailed that the accounts were combined, each in its own account's language, with a link to the account page and nothing about any yup. The address is kept encrypted in `account_notice`, bound to its row, for 7 days. Nothing is texted: the SMS campaign covers agreement updates only. Where neither account had an email address, nothing goes outside; the combined account shows `ACCOUNTS_COMBINED` in the app instead ("Notices in the app").
- **Afterwards.** Reviewers see a reported account's status as combined, with the account it went into and when, and its side of the yup as that account's; suspending or hiding content acts on the account it went into. A block B made through a place it had left is listed for A, and A can lift it there. A reviewer does not review a report by or about an account combined into theirs. Deleting A also removes what still refers to B: its revoked sessions and offers. Replaying the deletion log after a restore combines B into A again, through the same code, without telling anyone again (docs/operations.md, "Replaying deletions").

**An invitation sent to another address.** Opening an invitation named for an address or number the signed-in account does not have says only which kind it was sent to: "This invitation was sent to an email address that isn't on your account. Type it to add it and open the invitation." (`sent_to` in the preview: `kind` and `replaces`; nothing of the address, in full or in part). The invitation keeps whom it names as its blind index only, as before. The person types the address: `POST /v1/invitations/address/codes` (`token`, `identifier`) compares its index with the invitation's before anything is sent, and answers another with `NOT_INVITED_ADDRESS`, which says nothing more; the right one gets a code, under the usual limits. A number that replied STOP is answered `CODE_NOT_SENT`, as any address no code could go to, never `PHONE_OPTED_OUT`. Every try, at either call, is counted by account and by invitation, ten an hour each (`TOO_MANY_REQUESTS`). `POST /v1/invitations/address` with the address, its code and a proof of one of the account's own (`proof`, as for adding any; else `PROOF_REQUIRED`, before the code is looked at) adds it to the account and claims the invitation, named, so nobody has to confirm the person, in one transaction: a claim that fails leaves the address unadded. If the address belongs to another account, the answer is the offer to combine, and claiming the invitation afterwards opens it. If the account has another of that kind, the screen says that adding this one replaces it, which takes `replace: true` (else `IDENTIFIER_KIND_TAKEN`), asked before the code is looked at, and offers signing in with the invited address instead.

## Contact details at rest

No email address or phone number is stored in the clear: a dump, a backup or a query of the database shows none (`backend/src/contact`, migration 0025). A value that must be read back, to send to it or to show it to its owner, is **encrypted**; a value that must only be found or compared is kept as its **blind index**, a keyed hash; a value that was already a keyed hash stays one.

| Where | Holds | Kept as | Why |
|---|---|---|---|
| `account.email`, `account.phone` | the account's own address and number | encrypted, and indexed (unique) | sent to, shown to the owner, signed in by |
| `invitation.bound_email`, `bound_phone` | whom an invitation names | index only | a claim, and an address typed to add it ("Combining accounts"), is compared with it |
| `account_notice.email` | the email address a notice about its account goes to: combined, replaced or removed | encrypted, bound to its row, for 7 days | sent to |
| `one_time_code.identifier` | where a code went | index only | codes are found by it; the code is sent from the request |
| `sms_update.phone` | the number text updates were turned on with | index only | matched against the account's number and a STOP |
| `sms_opt_out.phone` | a number that replied STOP | index only (the key) | only ever matched |
| `sms_consent.phone` | the record of consent's number | encrypted and indexed; an opt-out the service records for a subscription it ends, the index alone | proof of what was agreed to, found from a number |
| `sms_code_consent.phone` | the number of a code asked for, only where it is the account's | encrypted | proof of what was asked for |
| `payment_handle.*` | payment options a person saved (Venmo, Cash App, PayPal.Me, Zelle) | encrypted | shown to their owner, and to a payer where shown ("Payment options") |
| `sms_code_consent.phone_hash` | every code consent's number | unchanged: HMAC under `APP_SECRET` | already keyed |
| `sign_in_limit.subject` | whom a limit counts (an address, a network, an account) | unchanged: HMAC under `APP_SECRET` | already keyed |
| `sms_inbound_seen`, `deletion_log`, `outbox.payload`, `outbox.last_error` | message IDs, account IDs, what a message is about, why it failed | nothing to protect | no address or number: the senders keep them out of errors |
| advisory locks of one-time codes | a lock per identifier | named by the index | the address never reaches the server |
| logs, metrics | — | none written | the development deliveries (`log`) write a code's email address, as always; never configured in a deployment |

- **Encryption** is XChaCha20-Poly1305 with a random 24-byte nonce. What is stored is one byte naming the key, the nonce, and the ciphertext with its tag; the table and column are the associated data, so a value copied into another column does not decrypt there. A value that does not decrypt is an error, never a guess.
- **The blind index** is HMAC-SHA256 of the normalized value (a lower-case email address, an E.164 number) with its kind, under an index key. The same value has the same index in every table, so lookups, joins and the unique constraints use it; `Ana@Example.com` and `ana@example.com` are one account.
- **One secret**, `CONTACT_DATA_KEY`. HKDF-SHA256 derives the encryption key and its ID byte from it, and once, from the first key, the index key, which the database keeps encrypted under the current key (`contact_key`). Rotating the key (`contact-data rotate`, with the old key as `CONTACT_DATA_KEY_PREVIOUS` meanwhile) re-encrypts everything and that row, and moves no index, so no lookup ever has to try two keys and an opt-out never fails to match the number it stops. The trade, and what to do if the key leaks: [docs/operations.md](docs/operations.md), "Contact data key".
- **Where values are decrypted**: sending an email, a code or a text; the account's own view (`GET /v1/me`, the number for text updates); re-encrypting under a new key (`contact-data rotate`); and, masked (`a•••@example.com`), the claimant an initiator confirms and the owner's `staff list`. A record of consent's number is also bound to the record's ID, so it does not decrypt in another record. The privacy policy says the same ("Security").
- **A fresh start.** Migration 0025 drops the plaintext columns and converts nothing, so it refuses to run, changing nothing, on a database where any of those tables holds a row (docs/deploy-render.md, "Contact data key", for the live one). A development database migrated by an earlier version of this change, or holding accounts from before it, is reset first: `docker compose down -v` for the compose database, or, for one of your own, `psql "$MIGRATION_DATABASE_URL" -c 'DROP SCHEMA public CASCADE; CREATE SCHEMA public; ALTER SCHEMA public OWNER TO pg_database_owner; GRANT USAGE ON SCHEMA public TO PUBLIC;'`, then `migrate` again. The trade: any later change to how contact details are stored, on a database with people in it, needs a migration that converts what is there.
- **Keys published in the repository** (`.env.example`, the tests, CI) are refused by every process wherever `WEB_ORIGIN` is not this machine, and by `migrate` and `contact-data` wherever the database is not; a key that decodes to printable text is refused everywhere. So the full Docker stack, whose database is another container, needs a key of your own (`docker-compose.yml`).
- **Backups made before this release** still hold plaintext until they expire, as the privacy policy says.

## Reviewing reports

Abuse reports are reviewed by staff the owner names, on the web app's `/staff` screen (`DESIGN.md` §9; `backend/src/review.rs`, `apps/web/src/screens/StaffPage.tsx`). A reviewer is an account in `staff_member`, which only the owner can write, with the `staff` command; they sign in with a one-time code like anyone, and the staff endpoints (`/v1/staff/...`) also want that code entered within the last 12 hours. To everyone else every staff path is "not found", and nothing in either app links to the screen. The staff endpoints are in the generated client like the rest, each described as "Staff only". The screen's words are in the `staff` part of the wording files, in English and Spanish.

- **The queue**: open reports, oldest first, with their age, reason and yup; one older than 24 hours is marked overdue. **A report**: what it says, who reported whom, and the reported yup's whole record, readable only while the report is open. Opening it is recorded. A reviewer never sees or decides a report they are part of (made, about them, or about a yup they hold or held a place in): to them it does not exist.
- **Decisions**: dismiss; hide the yup's content from the person reported; suspend their account; or both of the last two. Each needs a note, except dismissing. A report is resolved once, and the database refuses to change a resolution. Suspensions can be lifted and hidden content shown again, each with a note.
- **Hidden content**: for the person reported only, everything written in that yup reads "Hidden by review" in their language, in the exchange, its history and their copy of the record (which then says `content_hidden`, and leaves out each version's signed document, giving a `redacted` copy in its place, since that no longer matches its fingerprint), and signing or sending terms there is refused with `CONTENT_HIDDEN`. Names and amounts stay, and they can still end the yup. Nothing stored changes.
- **The audit history**: every report opened, every decision and undoing, every grant and revoke, and every suspension lifted by replaying the deletion log is a row in `review_event`, which neither the service nor the schema owner can change.
- **The alert**: a new report emails every reviewer through the outbox, saying only that a report is waiting, with a link to `/staff`; and the metrics `yuppers_reports_open` and `yuppers_reports_oldest_open_age_seconds`.

[docs/operations.md](docs/operations.md), "Reviewing reports", is the routine. `backend/tests/review.rs` checks all of it against a real database, and `apps/web/e2e/review.spec.ts` names a reviewer with the command and reviews a report through the screen.
