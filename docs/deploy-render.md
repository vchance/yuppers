# Deploying on Render

The owner's checklist for the first deployment of Yuppers: from creating the accounts to signing in on the live site and naming yourself a reviewer, then what to check, how to roll back, how backups work there, and what it costs. `render.yaml` at the root of the repository is the Blueprint it applies. [operations.md](operations.md) is the runbook for everything after; this page says where Render differs.

Render's documentation and prices were read on **2026-10-03**; both change, so check the pages linked here before relying on a detail. Nothing in this repository has a Render or Postmark account, and nothing here was tried against one: the steps marked **check** are the ones only the first real deploy can confirm.

## What the Blueprint creates

| Resource | Render type | What runs | Plan in `render.yaml` |
|---|---|---|---|
| `yuppers` | Web service, Docker, from the repository's `Dockerfile` | The image's default command, the api, serving the web app from the same origin (`WEB_DIR=/srv/web`); health check `GET /readyz`; before each deploy, `/usr/local/bin/migrate` | `0.5c-512mb`, one instance |
| `yuppers-worker` | Background worker, the same `Dockerfile` | `/usr/local/bin/worker`; before each deploy, `/usr/local/bin/migrate` too | `0.5c-512mb`, one instance |
| `yuppers-db` | PostgreSQL **17** | Database `yuppers`, owner user `exchange`; internal connections only | `0.1c-256mb`, 5 GB disk |
| `yuppers-settings` | Environment group | The plain settings shared by both services | |
| `yuppers-secrets` | Environment group | `SMTP_USERNAME` and `SMTP_PASSWORD` (asked for), `APP_DB_PASSWORD` (generated), and for text messages `SMS_ACCOUNT_SID`, `SMS_API_KEY_SID` and `SMS_API_KEY_SECRET` (entered by hand; "Text messages") | |

Everything is in `virginia` (US East). Render's regions are `oregon`, `ohio`, `virginia`, `frankfurt` and `singapore`, and services reach each other and the database privately only within one region ([Blueprint spec](https://render.com/docs/blueprint-spec), [private network](https://render.com/docs/private-network)). Render currently offers PostgreSQL 13 to 18 for new databases; the version cannot be changed after creation, so it is pinned to 17, the version the code, CI and the backup scripts use ([creating and connecting](https://render.com/docs/postgresql-creating-connecting)).

**The settings** (`.env.example` explains each):

| Setting | Value | Where |
|---|---|---|
| `WEB_ORIGIN` | `https://yuppers.app` (confirm the domain) | group `yuppers-settings` |
| `CODE_DELIVERY`, `NOTIFICATION_DELIVERY` | `smtp` | group |
| `SMTP_HOST`, `SMTP_PORT`, `SMTP_TLS` | `smtp.postmarkapp.com`, `587`, `starttls` | group |
| `SMTP_FROM` | `Yuppers <no-reply@yuppers.app>` (confirm the address) | group |
| `SMTP_USERNAME`, `SMTP_PASSWORD` | Postmark's Server API token, both | group `yuppers-secrets`, entered in the dashboard |
| `TRUSTED_PROXY_HEADER`, `TRUSTED_PROXIES` | `CF-Connecting-IP`, `1` ("Client addresses" below) | group |
| `SMS_DELIVERY`, `PUSH_DELIVERY` | `off` (`SMS_DELIVERY=twilio` once Twilio approves the campaign; "Text messages") | group |
| `SMS_ALLOWED_COUNTRY_CODES` | `+1` | group |
| `SMS_ACCOUNT_SID`, `SMS_API_KEY_SID`, `SMS_API_KEY_SECRET` | Twilio's account SID and a standard API key with its secret; unused while SMS is off | group `yuppers-secrets`, entered in the dashboard by hand |
| `SMS_FROM` | the Twilio number, `+1...`; unset while SMS is off | group, once SMS is on |
| `LOG_FORMAT`, `RUST_LOG` | `json`, `info` | group |
| Wallet settings | none, so passes are off | |
| `METRICS_ADDR` | unset ("Metrics" below) | |
| `APP_SECRET` | generated by Render | web service |
| `APP_DB_PASSWORD` | generated by Render | group `yuppers-secrets` |
| `MIGRATION_DATABASE_URL`, `DATABASE_SERVER_URL` | the database's internal connection string | each service |
| `MIGRATE_CREATE_APP_ROLE` | `true` | each service |
| `PORT` | `8080`, the port Render sends public traffic to | web service |

`generateValue: true` makes "a randomized, base64-encoded, 256-bit value" ([Blueprint spec](https://render.com/docs/blueprint-spec)): 44 characters, more than the 32 bytes `APP_SECRET` needs, and printable ASCII as `APP_DB_PASSWORD` requires. Neither is ever in the repository. A `sync: false` value is asked for once, when the Blueprint is first applied, and lives only in Render.

## The two database roles

The migrations grant to the restricted role `exchange_app` by name and need it to exist before they run; the owner, here Render's user `exchange`, runs them (`backend/migrations/README.md`). The owner's name is free: the migrations name only `exchange_app`. Render creates one user per database and documents adding users with `CREATE USER` ([credentials](https://render.com/docs/postgresql-credentials)), so its user may create roles, though not a superuser. Nobody can run `psql` before the first deploy from a Blueprint, so:

- **`migrate` creates the role.** With `MIGRATE_CREATE_APP_ROLE=true` it creates `exchange_app` with `APP_DB_PASSWORD` if the role does not exist, then applies the migrations, which grant to it as they always have. The password goes to the server only as a SCRAM-SHA-256 verifier, never in clear text. A role that already exists is left alone, its password included. Either way `migrate` refuses to go on if the role can do more than log in (superuser, create roles or databases, bypass row security, replicate, or be a member of the owner). `backend/src/app_role.rs`; `backend/tests/app_role.rs` tests it against a real server.
- **The api and the worker connect as `exchange_app`.** Render hands out the owner's connection string and nothing for another role, so the services get it as `DATABASE_SERVER_URL` and replace its user and password with `exchange_app` and `APP_DB_PASSWORD` (`database_url` in `backend/src/config.rs`). The owner's credentials in it are never used.
- **What this does not protect.** `MIGRATION_DATABASE_URL` is in both services' environments, because a pre-deploy command runs with its service's environment. The restricted role is what keeps the service's own queries from rewriting history (`DESIGN.md` §13.2); someone able to run code in the api's process could read the owner's string from the environment. Moving migrations out of the services would close that, at the cost of ordering deploys by hand.
- **If `migrate` says the owner may not create roles**, create the role once yourself, then deploy again ("Reaching the database" says how to connect):

  ```sql
  CREATE ROLE exchange_app LOGIN PASSWORD '<the APP_DB_PASSWORD value from the yuppers-secrets group>';
  ```

**Rotating the application role's password.** `migrate` never changes an existing password. Connected as the owner, `ALTER ROLE exchange_app PASSWORD '<new>'`, then at once set the same value as `APP_DB_PASSWORD` in `yuppers-secrets` and redeploy both services. Connections already open stay open; new ones fail between the two steps, so do it at a quiet time.

## Before you start

1. **The domain.** `yuppers.app` registered, with access to its DNS records.
2. **A Render account** at <https://dashboard.render.com>, signed in with the GitHub account that owns `vchance/yuppers`, and a payment method: pre-deploy commands and the database's backups need paid instances ([deploys](https://render.com/docs/deploys), [free instances](https://render.com/docs/free)). The **Hobby** workspace plan is enough to start; "Backups" below says when **Pro** is worth it.
3. **A Postmark account** at <https://postmarkapp.com>.
4. **The Render CLI** on your machine, for one-off commands: `brew install render`, then `render login` ([CLI](https://render.com/docs/cli)).
5. **Optional**: Docker or a Rust toolchain on your machine, for the fallbacks below.

## 1. Postmark

1. **Create a server** named `Yuppers`. Its default transactional message stream (`outbound`) is the one the service sends through; it sets no stream header, so Postmark uses that one ([SMTP](https://postmarkapp.com/developer/user-guide/send-email-with-smtp)).
2. **Add the domain** `yuppers.app` under Sender Signatures → Domains, and add the records Postmark shows at your DNS host ([verifying a domain](https://postmarkapp.com/support/article/1046-how-do-i-verify-a-domain)):

   | Type | Name | Value | Why |
   |---|---|---|---|
   | TXT | the selector Postmark shows, such as `20261003123456pm._domainkey` | the DKIM key Postmark shows | signs every message (DKIM) |
   | CNAME | `pm-bounces` | `pm.mtasv.net` | custom Return-Path: bounces go to Postmark, and the message passes SPF aligned with your domain |
   | TXT | `_dmarc` | `v=DMARC1; p=none; rua=mailto:<an address of yours>` | recommended by Postmark; tighten to `quarantine` once reports look clean |

   Postmark no longer asks for an SPF record: the Return-Path CNAME carries its SPF ([why](https://postmarkapp.com/blog/why-we-no-longer-ask-for-spf-records)). Both records usually verify within 48 hours. Click **Verify** for DKIM and for Return-Path.
3. **Request account approval.** Until Postmark approves the account it sends only to addresses on domains you have verified, so only `@yuppers.app` addresses would get codes ([approval](https://postmarkapp.com/support/article/1084-how-does-the-account-approval-process-work)). Review takes under a day on weekdays.
4. **Copy the Server API token** (server → API Tokens). It is both the SMTP username and the password. Keep it for step 2; never put it in the repository.

Postmark's SMTP is STARTTLS on port 587 (also 25 and 2525); it does not offer TLS from the first byte on 465, hence `SMTP_TLS=starttls`.

## 2. Render: apply the Blueprint

1. In the dashboard: **New → Blueprint**, connect GitHub if asked, and pick `vchance/yuppers`, branch `main`. Render reads `render.yaml` and lists what it will create ([infrastructure as code](https://render.com/docs/infrastructure-as-code)).
2. It asks for the `sync: false` values: paste the Postmark token as `SMTP_USERNAME` and again as `SMTP_PASSWORD`.
3. **Apply.** Render creates the database, builds the image once per service (a Rust release build: expect well over ten minutes the first time), runs `migrate` on a separate instance, then starts the new api and worker.
4. **Read the pre-deploy log** of the first deploy (web service → Events → the deploy). The lines are JSON; look for `"message":"build"`, `"message":"application role created"` and `"message":"migrations applied"`. The worker's pre-deploy says `application role already exists` if the web's ran first, or the other way round.

   **Check**: Render's documentation does not say whether a pre-deploy command is run directly or through `/bin/sh -c`; the image has no shell, so `render.yaml` names the binary itself, which works if Render runs it directly, as its examples of `dockerCommand` suggest ([Docker](https://render.com/docs/docker)). If the log says something like `/bin/sh: not found` instead, remove `preDeployCommand` from both services in `render.yaml`, run `migrate` from your machine as in "Reaching the database" (with `MIGRATE_CREATE_APP_ROLE=true` and `APP_DB_PASSWORD` set the same way), and redeploy; afterwards, run it before each release ([operations.md](operations.md), "Upgrading").
5. **Check** the web service's logs show `api listening` and no warning about `TRUSTED_PROXY_HEADER`, and the worker's show `worker started`, then `timers ran` within a minute.

Until the domain works, the app's pages load on the `onrender.com` address, but signing in there does not keep you signed in: cookie sessions are honored only from `WEB_ORIGIN`. To try it before DNS is ready, set `WEB_ORIGIN` in `yuppers-settings` to the `https://….onrender.com` address the dashboard shows, and set it back afterwards.

## 3. The domain

1. `render.yaml` names `yuppers.app` as the web service's custom domain, so it is listed under the web service's **Settings → Custom Domains**; Render adds `www.yuppers.app` and redirects it to the root ([custom domains](https://render.com/docs/custom-domains)).
2. At your DNS host ([other DNS providers](https://render.com/docs/configure-other-dns)):

   | Type | Name | Value |
   |---|---|---|
   | `ALIAS` or `ANAME` (or `A`, if neither is offered) | `@` (`yuppers.app`) | the service's `….onrender.com` host (for `A`: `216.24.57.1`) |
   | `CNAME` | `www` | the service's `….onrender.com` host |

   On Cloudflare DNS, use a `CNAME` at the root instead of an `A` record. Remove any other `A` or `AAAA` records at the root. If the domain has `CAA` records, they must allow `letsencrypt.org` and `pki.goog`.
3. Click **Verify**. Render issues and renews the TLS certificate itself and redirects HTTP to HTTPS. Because `WEB_ORIGIN` is HTTPS, every response carries HSTS.
4. **One origin.** The web app, the API and the app-association files (`/.well-known/apple-app-site-association`, `/.well-known/assetlinks.json`, served once `APPLE_APP_ID` and `ANDROID_SHA256_CERT_FINGERPRINTS` are set; [mobile-release.md](mobile-release.md)) all come from the same service at `https://yuppers.app`. Do not put the web app on another host: sessions, the content security policy and the links in emails all assume one origin.
5. Once the domain works, consider `renderSubdomainPolicy: disabled` on the web service in `render.yaml`, so the `onrender.com` address answers 404 and nobody uses it by mistake.

## 4. First sign-in

1. Open `https://yuppers.app`. The home page loads.
2. Sign in with your email address. The code arrives within seconds; Postmark's Activity tab for the server shows it delivered. In the received message's headers ("show original"), `dkim=pass` for `yuppers.app` and `spf=pass` for `pm-bounces.yuppers.app`.
3. Give your name and confirm your age, so that the account exists.

## 5. Naming yourself a reviewer

The `staff` command runs with the owner's connection, which the web service has as `MIGRATION_DATABASE_URL`. The image has no shell, and Render's dashboard shell and SSH do not work with distroless images ([SSH](https://render.com/docs/ssh)), so run it as a **one-off job**: a new instance from the service's latest build, with its environment, running one command, billed by the second ([one-off jobs](https://render.com/docs/one-off-jobs)). Jobs are started from the CLI or the API; the dashboard lists them under the service's **Jobs**.

```sh
render services                                  # note the web service's ID, srv-...
render jobs create srv-... --start-command "/usr/local/bin/staff grant you@example.com"
render jobs create srv-... --start-command "/usr/local/bin/staff list"
```

The job's log says `you@example.com now reviews reports`. Then open `https://yuppers.app/staff`; it asks for a fresh code if your sign-in is older than 12 hours.

**Check**, as for the pre-deploy command: if the job fails because it was run through a shell, run the same command from your machine with the external connection ("Reaching the database"):

```sh
# From a checkout of the repository:
MIGRATION_DATABASE_URL='<external URL>?sslmode=require' cargo run --manifest-path backend/Cargo.toml --bin staff -- grant you@example.com
# Or from an image built locally (docker build -t yuppers:local .):
docker run --rm -e MIGRATION_DATABASE_URL='<external URL>?sslmode=require' yuppers:local /usr/local/bin/staff grant you@example.com
```

## After going live: what to check

- [ ] `curl -si https://yuppers.app/healthz` and `/readyz` answer `204`.
- [ ] **The deployed build**: `curl -s https://yuppers.app/v1/meta` shows `commit` equal to the commit the web service's Events page says it deployed (the head of `main`), and `curl -sI https://yuppers.app/ | grep -i x-yuppers-version` shows its first seven characters. Your account screen ends with "Version 0.1.0 (…)" with the same seven characters. [operations.md](operations.md), "What is deployed", says how to match it to its CI run.
- [ ] Headers on `/`: `strict-transport-security`, `content-security-policy: default-src 'self'…`, `x-frame-options: DENY`, `x-content-type-options: nosniff`, `referrer-policy: no-referrer`, `x-request-id`.
- [ ] `https://yuppers.app/metrics` is the app's page, never metrics.
- [ ] A sign-in code arrives at an address outside `yuppers.app` (once Postmark has approved the account), and not in spam.
- [ ] The web service's logs (dashboard → Logs) are one JSON object per line, including a `build` line with the commit, and no warning about `TRUSTED_PROXY_HEADER` or a missing header.
- [ ] The worker's logs show `worker started`, its own `build` line, and `timers ran` about every minute. Two test accounts making a yup each get the notification email within seconds.
- [ ] `render jobs create srv-... --start-command "/usr/local/bin/staff list"` lists you.

## Text messages

Sign-in codes by SMS are off (`SMS_DELIVERY=off`) until Twilio has approved the messaging campaign: US carriers block or filter texts from a local number that is not registered for A2P 10DLC. The service needs only one number and sends only codes, so a **Sole Proprietor** registration fits (no business tax ID, one number per campaign). [operations.md](operations.md), "Codes by text message", says what the settings do. Twilio's pages read for this on **2026-10-04**: [Sole Proprietor registration](https://www.twilio.com/docs/messaging/compliance/a2p-10dlc/direct-sole-proprietor-registration-overview), [geo permissions](https://www.twilio.com/docs/messaging/guides/sms-geo-permissions), [API keys](https://www.twilio.com/docs/iam/api-keys), [requests to Twilio](https://www.twilio.com/docs/usage/requests-to-twilio).

In Twilio's console:

1. **Upgrade the account from trial** (add a payment method). A trial account texts only verified numbers.
2. **Buy a local number** able to send SMS (Phone Numbers → Buy a number, United States).
3. **Register a Sole Proprietor brand** (Messaging → Regulatory Compliance): first the Starter Profile with your name, email and US address, then the brand, which texts a one-time code to your own mobile number; answer it within 24 hours.
4. **Create the campaign** with the number. A Sole Proprietor brand offers a single use case, "Sole Proprietor", so the description has to say it is two-factor sign-in codes. Twilio links the campaign to a Messaging Service and adds the number to it as the sender; keep Twilio's default opt-out and help keywords (STOP, HELP). Suggested text:
   - **Description**: "One-time sign-in codes for Yuppers (yuppers.app), sent only when the user types their phone number on the sign-in page."
   - **How users opt in**: "The user enters their own phone number on yuppers.app's sign-in screen and asks for a code. We only text that number, only with a code, only in reply to that request."
   - **Sample messages**, exactly as the service sends them (`backend/src/notifications/sms.rs` tests them):
     - "123456 is your Yuppers sign-in code. Do not share it with anyone."
     - "123456 es tu código de Yuppers para entrar. No se lo des a nadie."

   Vetting is manual and can take weeks; resubmitting after a refusal costs a further fee.
5. **Geographic permissions** (Messaging → Settings → Geo permissions): the **United States only**; untick everything else, Canada included, unless it is served. Keep `SMS_ALLOWED_COUNTRY_CODES=+1` in Render: it is the service's own check, and the geo permissions keep out the rest of `+1`.
6. **Create a standard API key** (the **API keys & tokens** page) and copy its SID (`SK...`) and secret; the secret is shown once. A key can be revoked without touching the account, which is why it is preferred to the auth token. Copy the **Account SID** (`AC...`) from the same page.

Then in Render, once the campaign is approved:

1. **Environment Groups → `yuppers-secrets`**: add `SMS_ACCOUNT_SID`, `SMS_API_KEY_SID` and `SMS_API_KEY_SECRET`. `render.yaml` lists them, but Render does not prompt for a `sync: false` value in an environment group, or for one added to a Blueprint already applied ([Blueprint spec](https://render.com/docs/blueprint-spec)), so enter them by hand. Leave `SMS_AUTH_TOKEN` unset: the api refuses to start with both kinds of credential.
2. **`yuppers-settings`**: `SMS_FROM` = the number, `+1...` (or the Messaging Service's `MG...` SID), and `SMS_DELIVERY=twilio`. Change `SMS_DELIVERY` in `render.yaml` too, or the next Blueprint sync sets it back to `off`.
3. The api restarts with the new settings. If one is missing or malformed, it stops at start and its log names the setting (never the secret); the old instance keeps serving.
4. **Check**: `curl -s https://yuppers.app/v1/meta` lists `"phone"` in `sign_in_channels`; ask for a code for your own phone; it arrives in one message; Twilio's Messaging logs show it delivered.

## Client addresses

Each signature records the requester's address, and the sign-in limits count by it (`DESIGN.md` §8), so the service must read the real one. Every request to a Render web service passes through Cloudflare, which "writes [`CF-Connecting-IP`] on every request that reaches a Render web service, and it overwrites whatever the caller sent", while it appends to `X-Forwarded-For`, so "a caller who sends their own copy of the header controls the leftmost entry" ([Render, hosting PocketBase](https://render.com/articles/host-pocketbase-on-render)). Requests seen on Render carry more than one hop in `X-Forwarded-For` (the client, a Cloudflare edge, an internal hop), so the count of trusted entries would be 3, not 1, and is not documented. Hence `TRUSTED_PROXY_HEADER=CF-Connecting-IP` with `TRUSTED_PROXIES=1`: one address that the caller cannot set. Traffic over Render's private network does not pass through Cloudflare and has no such header; the api then warns about once a minute and counts the request as its peer, which only matters if something private calls the api.

**Check** after going live: no warnings that the header is missing, and the address on a test signature (`acceptance_network_metadata`, as the owner) is yours.

## Metrics

`METRICS_ADDR` stays unset: Render forwards one port of a web service to the internet (`PORT`, set to the api's 8080), and the metrics are never on it. To collect them, set `METRICS_ADDR=0.0.0.0:9100` on the web service (not in the shared group) and scrape `http://<the service's internal host>:9100/metrics` from a scraper running as another service in the same region, such as a private service running Prometheus or Grafana Alloy: web services can listen on further ports for private network traffic only ([web services](https://render.com/docs/web-services), [private network](https://render.com/docs/private-network)). Background workers have no internal address and cannot be scraped; the api's own metrics include the outbox and report gauges, read from the database, and the worker's logs show its passes. If the worker's own metrics are wanted, run it as a private service (`type: pserv`) with `METRICS_ADDR` set instead.

## Reaching the database

The database accepts internal connections only (`ipAllowList: []`). For anything from your own machine (a backup, a restore, a fallback command), add your address on the database's **Access Control** page for the time it takes, and use the **External Database URL** from its Info page with `?sslmode=require` ([creating and connecting](https://render.com/docs/postgresql-creating-connecting)). Remove the address afterwards. Syncing the Blueprint again may also reset the list to `[]`, which is the safe direction. That URL is the owner's: never paste it into a chat, an issue or a commit.

## Backups

**What Render provides** ([backups](https://render.com/docs/postgresql-backups)):

- **Point-in-time recovery** on every paid database: the past **3 days** on a Hobby workspace, **7 days** on Pro or higher. A recovery creates a **new database instance**, and the services must then be pointed at it. It cannot restore to within the last ten minutes. Upgrading to Pro does not extend the window back in time.
- **Logical backups** made on demand from the dashboard and kept for 7 days. Nothing is taken daily by itself.
- **Free databases** have no backups at all and expire after 30 days ([free](https://render.com/docs/free)): never use one for real data.

**How it fits ours.** Recovery is Render's own copy, inside Render. `scripts/backup.sh` writes a copy that does not depend on Render and that the restore drill proves ([operations.md](operations.md), "Backups"). The deletion log matters after **every** restore, Render's included: a recovery to an earlier time brings back accounts deleted since, with their addresses and sessions, until the deletion log is replayed.

**Restoring with Render's recovery**, step by step:

1. Before anything else, export the live database's deletion log if it can still be reached (`scripts/export-deletions.sh` with the external URL; [operations.md](operations.md), "Replaying deletions"). Otherwise use the newest `.deletions` file kept beside a backup.
2. **Suspend** both services (dashboard → service → Suspend), so nothing writes to either database meanwhile.
3. Recover to the chosen time in the dashboard. The new instance holds the roles as they were, `exchange_app` and its password included, since the recovery is of the whole server.
4. Replay the deletion log into the new instance as `exchange_app`, from your machine: `scripts/replay-deletions.sh -d 'postgresql://exchange_app:<APP_DB_PASSWORD>@<new external host>/yuppers?sslmode=require' deletions.txt`, and read its report.
5. Point both services at the new instance: in `render.yaml`, change `fromDatabase.name` for `MIGRATION_DATABASE_URL` and `DATABASE_SERVER_URL` to the new instance (or set them in the dashboard), then resume both services. The pre-deploy `migrate` applies anything newer than the recovery point.

**Recommendation.**

- A paid database from day one; never the free one.
- Start on Hobby (3 days of recovery). Move the workspace to **Pro** (7 days) once real people's agreements are stored, since a problem noticed after a long weekend would otherwise be past reach.
- Weekly, and before any risky change, run `scripts/backup.sh` from your machine against the external URL and keep the dump and its `.deletions` file encrypted, off Render, as long as the retention decision allows ([operations.md](operations.md), "Decisions still open"). Run `scripts/export-deletions.sh` daily, which closes most of the gap between dumps for deletions. Do the restore drill monthly.
- Do not run the backup from GitHub Actions: the dump holds every person's contact details, and this repository is public.

## Rollback

- **Code.** On the service's Events page, pick an earlier successful deploy and roll back to it; Render redeploys that build ([rollbacks](https://render.com/docs/rollbacks)). Roll back the api and the worker together. **Check** whether a rollback turns off automatic deploys for the service, and turn them back on once the fix is on `main`.
- **Migrations are not rolled back.** The older code then runs against the newer schema, as it does for a few minutes in every deploy ([operations.md](operations.md), "Upgrading"). A release whose migration the old code cannot live with says so in its notes; then the way back is a database recovery (above), not a rollback.
- **Settings.** Environment group changes take effect when the services next deploy or restart; changing one back is a rollback of its own.

If a Rust release build twice per deploy uses up the pipeline minutes, the image can instead be built once by CI, pushed to a registry, and deployed to both services as a prebuilt image; prebuilt images are deployed by hand or by API, not automatically ([web services](https://render.com/docs/web-services)).

## What only the first deploy can confirm

- That Render runs `preDeployCommand` and a one-off job's start command without a shell (step 2, step 5).
- That Render's database user may create roles: its documentation implies it and does not say so (`migrate` names the problem, and "The two database roles" gives the one-time `psql` step).
- That `RENDER_GIT_COMMIT` reaches the Docker build as a build argument. Render passes the service's own environment variables as build arguments; whether its built-in ones go too is not stated. The api and worker fall back to `RENDER_GIT_COMMIT` at run time, which is documented, so `/v1/meta` names the commit either way; the web app's version line then lacks the commit until this is settled, for example by having CI build the image.
- That `RUN --mount=type=cache` in the `Dockerfile` works on Render's BuildKit builders. Render uses BuildKit and caches layers; the cargo cache likely does not persist between builds, which makes builds slower but not wrong.
- That `CF-Connecting-IP` is present on every request ("Client addresses").
- That Twilio takes the first text message. Nothing has been sent through Twilio; the requests are checked against a stand-in (`backend/tests/sms.rs`), written from its documentation ("Text messages").
